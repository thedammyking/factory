# build

The factory skill reads this when a run takes the build route, and whenever it is sent to a step of **build** (from **Approve** or another reference). Its numbered steps are the steps of **build** the skill and the other references name.

A stage below is dispatched the way triage is: `run-state dispatch <stage>`, the named agent in the background with its model from `.factory/config.json` when set, the agent's id recorded with `--agent`, a one-line `<what it does> <id>.`, and the end of your turn. Its prompt is triage's three lines, with the `base_sha` the lane printed, plus any line the stage names. When its notification arrives, ignore its text and read the stage's file. A stage whose file is missing or lacks what the step names is incomplete, a factory error: write `attention-<stage>.md` (options: `/factory <the request>` to start again in a new run, `/factory abandon <id>`), run `run-state set stage failed --run <id>`, print it and stop.

1. **Lane.** `run-state lane --run <id>` switches the run worktree to the lane's branch and prints `on <branch> from <base> at <sha>`. If it exits non-zero, write `attention-lane.md` quoting its error, run `run-state set stage failed --run <id>`, print it and stop. Otherwise the claim follows (**Request issue** in the skill).
2. **Research.** On a run started from a map's run list (its state has `map`), do step 3 of **From a run list** in `references/map.md` first. Stage `research`, agent `factory:researcher`, model `models.research`, with the line `mode: research`: `Researching <id>.` Read the last `Status:` line of `<run_dir>/research.md`.
   - `ok` or `partial(<reason>)`: `run-state done research --run <id>`, then the grill.
   - `blocked(<reason>)`: write `attention-research.md` quoting the reason (options: `/factory <a request this repo can hold>`, `/factory abandon <id>`), run `run-state set stage needs-human --run <id>`, print it and stop.
3. **Grill.** In this session, not a dispatch, and the last time the run asks the human anything it can decide: after it, the run goes on its own to the PR (#81). Load the `factory:grilling` skill and follow it, with these rules over it:
   - The facts are in `research.md`, `triage.md` and `prompt.md`. On a run started from a run list, the map's decisions are answered, as step 4 of **From a run list** says. When a question needs a fact none of them holds, run `run-state dispatch fact --run <id>` (an exit 4 goes to **Caps** in the skill), then dispatch `factory:researcher` in the foreground, with `models.research` as its model when set and a stage's three lines plus `mode: fact` and `fact: <the question>`. When it returns, run `run-state dispatch fact --agent <its id> --run <id>` and `run-state done fact --run <id>`, read the `## Fact:` section it appended to `research.md`, then ask. A fact it records as `- Unknown:` stays there for the planner, never asked. `fact` is this step's stage: a run stopped at its cap, cut off in it, or with it last on resume's `done:` line goes on at this step.
   - Ask in the project's grill mode, `grill` in `.factory/config.json`, as the skill says. Ask only decisions (what done looks like, scope, what a user sees), each with its recommended answer, until every criterion the spec needs is a test or an observable result.
   - Each `- Toolchain:` line in `research.md` is a decision, since no ticket can install a tool on this machine: upgrade (or install) the tool, or build on versions the machine already runs. On upgrade, append the answer and run the install yourself, with the machine's own package manager (`brew install cocoapods`, `nvm install 24 && nvm alias default 24`, the tool's documented installer), then check it the way the line names it (`pod --version`) through `env -i PATH="$PATH" HOME="$HOME"`, the environment the implementer gets. Found there, carry on with the grill. Not found, or the install fails or is refused, print the command and `/factory resume <id>`, to be run in a new session because the implementer inherits this session's `PATH`, and stop: the grill goes on there.
   - A run started from a map's run list (its state has `map`) asks nothing: the map was its grill. Each question takes the map's decision when `map.md` or `decisions/` records one, as step 4 of **From a run list** in `references/map.md` says, else its recommended answer, marked `(default)`, and the session heading is `### Session <today's date> (from the map: the factory's calls)`. A `- Toolchain:` line takes its recommended answer too, and an upgrade is installed as above.
   - After each call, append the settled pairs to `<run_dir>/grill.md`, which starts with `## Clarifications`, under `### Session <today's date>`, one `- Q: <question> → A: <answer>` line each, in the human's words.
   - Unattended, when `<run_dir>/grill-answers.md` exists, nothing is asked in chat: each question takes its answer from that file, else its recommended answer marked `(default)`, and the session heading is `### Session <today's date> (unattended: answered from grill-answers.md)`.
   - When nothing is left to ask, `run-state done grill --run <id>`.
4. **Spec.** Stage `spec`, agent `factory:planner`, model `models.plan`, with the line `mode: spec`: `Writing the spec for <id>.` It writes `<run_dir>/spec.md`, which must hold `SC-001`. Then `run-state done spec --run <id>`, and the builder check after the first spec, the spec approval after a revision.
5. **Builder check.** Stage `builder-check`, agent `factory:builder-check`, model `models.builder_check`: `Checking the spec for <id>.` Sort each question in `<run_dir>/builder-check.md`:
   - **answered**: `spec.md`, `grill.md` or `research.md` already answers it;
   - **minor**: a builder could settle it without changing what gets built, so its default is the factory's call;
   - **theirs**: only the human can answer it, and the answer changes what gets built.

   Nothing is asked: the grill is over, so a theirs takes its default too, the call the PR lists for the human to review (unattended: from `grill-answers.md`, else the default). Append every question to `grill.md` under `### Session <today's date> (builder check)`, or `(builder check; unattended: answered from grill-answers.md)`: `→ A: <answer> (from <file>)` or `→ A: <default> (the factory's call)`. Run `run-state done builder-check --run <id>`. Unless `spec.md` itself answered every question, go to **Spec** once so the spec carries the answers. The builder check never runs twice.
6. **Spec approval.** The factory's own, with no stop: the grill settled what the human decides, and the PR is where they review the result (#81). Run `run-state approve spec approved --run <id>`, then the **Notion push** and the tracker's **Spec approval** (**Request issue** in the skill), print a markdown link to the spec, `[spec.md](<run_dir>/spec.md)`, with its title and its counts of requirements and criteria, never the spec itself, and go on to step 7. If `approve` refuses, the run isn't where this step is: print why and stop.
7. **Tickets.** Stage `tickets`, agent `factory:planner`, model `models.plan`, line `mode: tickets`: `Cutting <id> into tickets.` It writes `<run_dir>/tickets/NN-<slug>.md` from `01-`. Then `run-state done tickets --run <id>`, which checks that the frontier can order the tickets and records them as they are; nobody approves them. If it exits non-zero, dispatch the stage once more with the line `problems: <the reasons it printed>`, then run `done tickets` again. If that fails too, write `attention-tickets-cut.md`. Its headline asks whether to cut the tickets again; What happened quotes the refusal's reasons; Evidence lists `tickets/` and `spec.md`; the options are Cut again (recommended: dispatch the stage once more with the `problems:` line, which costs one more dispatch and may be refused again) and `/factory abandon <id>`. Run `run-state set stage needs-human --run <id>`, print it and ask its question with the options Cut again and Abandon. On Cut again, dispatch the stage with the `problems:` line and run `done tickets` again, and a refusal asks again. Once `done tickets` exits 0, the tickets go to the tracker as its **Tickets** says (**Request issue** in the skill).
8. **Next ticket.** `run-state next-ticket --run <id>`. It lists the tickets that block others first, so what unblocks the most is built first and the tickets behind it then go side by side (#81). Take each `NEXT <NN-slug>` line: `run-state ticket <NN> in-progress --run <id>`, then plan it. `STARTED` and `WAIT` lines need nothing; with only those, end your turn. On `DONE`, read `${CLAUDE_PLUGIN_ROOT}/skills/factory/references/review.md` and follow it. On `BLOCKED` lines, this version stops: write `attention-tickets.md` quoting them (options: `/factory abandon <id>`), run `run-state set stage needs-human --run <id>`, print it and stop.
9. **Plan.** Stage `plan:<NN>`, agent `factory:planner`, model `models.plan`, lines `mode: plan` and `ticket: <NN-slug>`: `Planning ticket <NN> of <id>.` Read the `status:` line of `<run_dir>/tickets/<NN>/plan.md`. On `ready`, `run-state done plan:<NN> --run <id>` and implement it. On `reroute`, a oneshot's plan lists more than one product file: `run-state reroute --run <id>` marks the plan done and makes the run a build on the same branch and worktree. Go to step 2. On `open_questions`, nothing is asked: answer each with the answer the plan, `spec.md` and `research.md` suggest, the one that keeps closest to the spec, and append them to `grill.md` under `### Session <today's date> (ticket <NN>; the factory's calls)` as `- Q: … → A: … (the factory's call)` lines, which the PR lists. Then plan the ticket again, once: a plan still at `open_questions` after that writes `attention-plan-<NN>.md` listing them (options: `/factory resume <id>` to answer, `/factory abandon <id>`), runs `run-state set stage needs-human --run <id>` and asks them in place of the item's question, each with 2 to 4 options, and their answers go to `grill.md` in the human's words before the ticket is planned again.
10. **Implement.** Read `${CLAUDE_PLUGIN_ROOT}/skills/factory/references/implement.md` and follow it for ticket `<NN>`. It ends at a stop, or at step 8 once the ticket is merged.
