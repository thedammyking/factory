# Implement one ticket

The factory skill reads this at step 10 of **build**, once ticket `<NN>`'s plan is `ready`. `run-stage.mjs` does the work: it runs the implementer as a `claude -p` child in the ticket's own worktree, has `verify --full` judge what it left, and ends its output with one verdict line, `<WORD> <NN>: <why>`. You act on that word. The rounds and their caps are the scripts': never start an attempt that a step below doesn't name.

Up to `parallel_tickets` tickets go through these steps at once, each in its own worktree. A notification is about one ticket, the one its verdict names, so act on it for that ticket alone. The next ticket starts when one of yours is merged, at step 8 of **build**: never wait on another run's tickets.

`run-stage.mjs` sits beside `run-state.mjs` in the skill's scripts directory. Call it as `node <that directory>/run-stage.mjs <command> <NN> --run <id>`, written out in full (called `run-stage` below), always with Bash's `run_in_background`, since a child runs for many minutes. Say the step's line and end your turn. When the completion notification wakes you, read the background task's output for its last line, the verdict, and ignore the notification's own text.

Before the ticket's first attempt, run `run-state next-ticket --run <id>`. A `WAIT <NN-slug>: …` line for this ticket means its code map shares a file with a ticket already started: run `run-state ticket <NN> ready-for-agent --run <id>`, print the line and go to step 8 of **build**. The ticket is planned again when it next starts. Otherwise go to step 1.

1. **Attempt.** `run-stage implement <NN>`: `Implementing ticket <NN> of <id>.` Print any `WARN` line it printed. If it exited 4, it printed run-state's `BUDGET` lines: go to **Caps** in the skill, with the stage `implement:<NN>`, once nothing else runs (see the end). Otherwise, by the verdict:
   - `MERGE`: go to step 2.
   - `QA`: read `references/qa.md` beside this file and follow it for ticket `<NN>`.
   - `ROUND`: run `run-state round implement:<NN> --run <id>`, in the foreground. On `OK …`, go to step 1. On exit 5, its `ESCALATE …` line means the rounds are spent: stop (below), quoting both lines, and recommend reading the last report and the evidence before deciding. When it says `rounds`, add the option `run-state override implement_rounds "<reason>" --run <id>`, written out in full, followed by `/factory resume <id>`.
   - `AMEND`: the plan was wrong about the code, and the ticket's commits are gone. Plan the ticket again as step 9 of **build** does; the planner amends the plan from `tickets/<NN>/implementation.md`. On `ready`, go to step 1, which starts a fresh child.
   - `RESEARCH`: the implementer needs a fact from outside the repo. Dispatch stage `context:<NN>` the way **build** dispatches a stage: agent `factory:researcher`, model `models.research`, lines `mode: context` and `ticket: <NN-slug>`, and the line `Researching ticket <NN>'s question.` When it's done, `tickets/<NN>/context.md` must end with a `Status:` line, else the stage is incomplete. Run `run-state done context:<NN> --run <id>` and go to step 1, which resumes the child with the answer.
   - `ATTENTION`: stop (below).
   - `SUSPENDED`: the child stopped at the usage limit, which costs no round, so never run `round` for it. Stop (below), with the options `/factory resume <id>` (once the limit resets) and `/factory abandon <id>`, and `run-state set stage suspended --run <id>` in place of needs-human. Nothing resumes it but the human: schedule no wake-up and no retry.
2. **Merge.** `run-stage merge <NN>`: `Merging ticket <NN> into <id>'s branch.` Merges wait on each other, so ticket branches go into the run branch one at a time. On `MERGED`, the ticket is done: its sub-issue closes as the tracker's **Tickets** says (**Request issue** in the skill), then go to step 8 of **build** for the next one. On `ATTENTION`, stop: a conflict was aborted, the run head went red after merging two green sides, or it was red already.

To stop, write `attention-implement-<NN>.md`. Its headline is the verdict's reason; What happened quotes the verdict line, and the `ESCALATE` line when there is one; Evidence lists `tickets/<NN>/implementation.md` with its `implementation.round<N>.md` files, `tickets/<NN>/evidence.json` (`evidence.json` after a merge), `tickets/<NN>/qa.json` when there is one, and `logs/implement-<NN>.*.jsonl`. When the report says `intent_gap`, the recommendation says what the spec leaves open. The options are `/factory abandon <id>`, but for `BLOCKED: environment` (below). Run `run-state set stage needs-human --run <id>`, print it and stop.

When the report says `BLOCKED: environment`, What happened lists each command under its `denied:` list and under `Denied, as the child's result records it:`, each next to the rule that would allow the part that was denied: `Bash(<program> <subcommand>:*)`, its program and the word after it, past any `cd <dir> &&` or `NAME=value` before them (`Bash(<program>:*)` for a program run alone). With a command to allow, the options are Allow and retry (recommended: `run-state allow "<rule>" --run <id>` for each rule, then `run-stage implement <NN> --run <id>`, chained with `&&` and written out in full, which resumes the child's session with the ticket's commits at no round's cost, while each rule stays in the recipe's `allow` list for later runs, where the PR shows it) and `/factory abandon <id>`. With none, the options are `/factory abandon <id>` alone. On Allow and retry, run each `allow` in the foreground. It refuses a rule that would allow every command, and prints `allowed already` for a rule the recipe holds, which didn't cover what was denied: say so for each. Once one rule is newly allowed, go to step 1; with none, stop again with Abandon alone.

While another ticket's stage still runs in the background, a stop waits for it, and nothing new starts. That ticket goes on through these steps to its own merge or stop, but never to step 8. Once nothing runs, set the stage, print each attention item and stop.
