# Review the run

The factory skill reads this at step 8 of **build**, once `next-ticket` prints `DONE`: every ticket is merged into the run branch, each built on its fast checks alone. The run's checks in full, `qa`'s walk and the review now judge every ticket together, and what they find is fixed together (#81). Read-only lenses judge the diff in parallel, `synthesize.mjs` turns their findings, the run's red checks and `qa`'s failed criteria into `findings.json`, and only open P0s and P1s go round, `caps.review_rounds` (2) times at most. A lens's `ask` is a judgment call the fix round makes like any fix, recording it for the PR (#81): a review never stops to ask the human. The rounds and their cap are the scripts': never start a round that a step below doesn't name.

The scripts sit beside `run-state.mjs`. Call each as `node <that directory>/<script> … --run <id>`, written out in full.

First, once per review and never on a re-review, run `sync-base.mjs before-review`, so review sees the tree that will merge. Then, whatever it printed, run `verify.mjs --full` with Bash's `run_in_background`, say `Verifying <id> in full.` and end your turn: the run head has had only fast checks. When it wakes you, walk the run: read `references/qa.md` beside this file and follow it, which brings you to step 1. On exit 3 (`CONFLICT …`) the base's merge stopped at conflicts, the factory's to settle (#81): run `run-stage.mjs resolve` with Bash's `run_in_background`, say `Resolving <id>'s merge of its base.` and end your turn. When it wakes you, read its last line: `RESOLVED` goes to the walk, its full verify done; `SUSPENDED` stops as step 5's does; `ATTENTION` stops (below). On exit 1 GitHub or git refused it, wrote `attention-sync.md` and ended the run needs-human: run the snapshot (see **Ending a run** in the skill), print that item and stop. Any other non-zero exit is a factory error: stop (below).

1. **Package.** Run `review-package.mjs`, `classify-diff.mjs` and `security-scan.mjs`, in that order. `security-scan` exits 1 when a capability failed or is missing, which the merge decision reads later: go on. Any other non-zero exit is a factory error: stop (below). Then read `<run_dir>/evidence.json` and `<run_dir>/touches.json`. Unless `evidence.json`'s `sha` is `touches.json`'s `head`, and it has `green: true` or `red_cause: introduced`, stop. A red the run introduced is no stop: each failing check is a finding of its own, which the fix round fixes with the lenses' (#81).
2. **Captures**, only when `touches.json` has `ui` hit and some `tickets/<NN>/plan.md` has a `## UI states` section. A `ui` hit with no UI state in any plan (an email template, a component no screen shows yet) has nothing to picture: skip this step and the UI lens, never stop for it, and the code lens reviews those files (#81). Otherwise write `<run_dir>/ui-states.json` as `{"states": [...]}`, one state for each line under `## UI states` in every `tickets/<NN>/plan.md`:
   - `name`: `<NN>-` and the state, in lowercase words joined by `-`;
   - `url`: `http://localhost:{port:<app>}<route>`, `<app>` being the recipe's app that serves the route;
   - `setup` and `actions`: what the line's "how to reach it" says, in `capture-states.mjs`'s terms. `setup` takes `block` and `hold` (lists of URL patterns, for an error and for loading) and `localStorage` (`{key: value}`, for a returning visit). `actions` is a list of `{fill: [selector, text]}`, `{click: selector}`, `{hover: selector}`, `{focus: selector}`, `{press: key}`, `{waitFor: selector}` and `{wait: ms}`, its selectors taken from the plan's own words (`text=Export CSV`, `role=button[name="Export CSV"]`).
   - Sign in once (#81): a state that needs a signed-in user takes `"signedIn": true`, and the file's `signIn` (`{url, actions}`, the plans' sign-in steps, as the test user) or, for a mobile app, `mobileSignIn` (`{app, flow}`) is the one sign-in every such state starts from. Never write a sign-in into a state's own actions: each picture would sign in again, and an app that limits sign-ins makes every one wait. Only a state of the sign-in itself leaves `signedIn` out.
   - A state of a mobile app is `name`, `app` (the recipe's mobile app) and `flow` in place of `url`, `setup` and `actions`: the Maestro commands, each as JSON, that reach the state from a fresh launch, taken from the plan's words (`{"tapOn": "Cart"}`, `{"openLink": "shop://cart"}`). `capture-states` pictures it on the run's device, in light and dark at the default and largest text size.

   Then run `run-apps.mjs up`, `capture-states.mjs <run_dir>/ui-states.json`, and `run-apps.mjs down` whatever happened. A capture that failed (exit 1) is the UI lens's to judge: go on. If `up` failed or `capture-states` exited 2, stop.
3. **Lenses.** Dispatch each lens the diff earns: `code` always, `ui` when step 2 pictured states, `security` when any of `auth`, `data`, `network`, `files`, `crypto` or `ci` hit. Dispatch them one after another, each in the background, so they run at the same time:
   - `run-state dispatch review-<lens>`, which moves the lens's last file aside as a round first. Exit 4 is the **Caps** of the skill, with the stage `review-<lens>`.
   - The `factory:reviewer-<lens>` agent in the background, with its model from `.factory/config.json` when set: `models.review_code`, `models.review_ui` or `models.security`. The prompt is triage's three lines, and on a re-review the line `fix_diff: <run_dir>/review-fix.diff`.
   - `run-state dispatch review-<lens> --agent <agent id>`.

   Say `Reviewing <id>.` and end your turn. Each completion notification wakes you: ignore its text, and once every lens dispatched has finished, read their files.
   - A `review-<lens>.md` that's missing or has no `verdict:` line, or a `review-ui.md` whose first line isn't `disposition: …`, was cut off: dispatch that lens once more, fresh, as above (synthesis never counts a round with no verdict). Cut off twice is a factory error: stop.
   - A `review-ui.md` whose first line is `disposition: recapture` judged pictures that missed their states: run step 2 again and dispatch the UI lens once more. A second `recapture` goes on to synthesis, where its findings are the human's.

   Then run `run-state done review-<lens>` for each.
4. **Synthesis.** `synthesize.mjs`, then by the `disposition` on its first line:
   - `ship`: the review is clean. Read `references/pr.md` beside this file and follow it.
   - `ask`: only a person's question on the PR is (the human lens, read on a resume): stop, and What happened lists each open human ask from `findings.json`, with its id, severity, location and claim.
   - `fix`: step 5. Its open findings include the run's red checks (the `verify` lens) and `qa`'s failed criteria (the `qa` lens).
5. **Fix round.** `run-state round review`, in the foreground. Exit 5 prints `ESCALATE …`: the rounds are spent. With no open P0 in `findings.json`, that is no stop (#81): what's left is the human's to judge on the PR, where it costs them a read rather than a reply. Read `references/pr.md` beside this file and follow it: its decision is needs-human on the open P1s, and the PR lists each of them. With an open P0, stop, quoting the line and listing the open P0 and P1 fixes, with the option `run-state override review_rounds "<reason>" --run <id>`, written out in full, followed by `/factory resume <id>`. On `OK …`, run `run-stage.mjs review-fix` with Bash's `run_in_background`, say `Fixing <id>'s review findings.` and end your turn. When it wakes you, read the last line of its output, ignoring the notification's text. Exit 4 is the **Caps** of the skill, with the stage `review-fix`. Otherwise, by its first word:
   - `REVIEW <lens,…>`: with `qa` among them, walk the criteria its findings name again first, as `references/qa.md` says with its `criteria:` line, which brings you to step 1. Then, or with no `qa`: step 1 again, then step 2 when `ui` is among the lenses so the UI lens sees the fix, with `--only <state,…>` added to `capture-states.mjs`: the states the open UI findings' locations name, which the fix was for, while every other state's pictures stand, then step 3 for only the lenses it names, each with the `fix_diff` line, then step 4. `verify` and `qa` are no lens agents: the round's own green verify settled the first, and the walk again the second, so leave them out of step 3. Nor is `human`: once the others are read, go to step 3 of `references/comments.md` in place of step 4. With no lens agent named, dispatch nothing and don't end your turn.
   - `ROUND`: step 5 again.
   - `SUSPENDED`: the child stopped at the usage limit, which costs no round. Stop, with the options `/factory resume <id>` (once the limit resets) and `/factory abandon <id>`, and `run-state set stage suspended --run <id>` in place of needs-human.
   - `ATTENTION`: with no open P0 in `findings.json`, what the fix couldn't settle is the human's to judge on the PR (#81), as on `ESCALATE`: read `references/pr.md` beside this file and follow it. With an open P0, stop.

To stop, write `attention-review.md`. Its headline is the reason; What happened quotes the line that stopped it; Evidence lists `findings.json`, `deferred.md`, each `review-<lens>.md` with its `review-<lens>.round<N>.md` files, `review-fix.md`, `evidence.json`, `qa.json` and `logs/review-fix.*.jsonl`, those that exist. The options are `/factory abandon <id>`. Run `run-state set stage needs-human --run <id>`, open the draft PR as **Draft** in `references/pr.md` says (never on `SUSPENDED`, which a resume carries on), then the snapshot; print it and stop.
