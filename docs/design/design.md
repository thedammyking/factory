# Borrow the Contracts, Skip the Daemons

None of the 33 tools and repos examined is the factory you described, and the three that come closest (marshal-factory, Archon, no-mistakes) are daemons or servers with their own databases, not Claude Code plugins. What they share, and what a plugin can copy cheaply, is a set of **stage contracts**: a typed triage verdict (Archon), a plan file whose `status` field is the state machine (bmad), a fresh implementer that reads only its plan and reports to a file (bmad, Superpowers), a verification script whose output is tamper-evident evidence pinned to a commit SHA (marshal-factory), per-step fix budgets that fail closed to a human (no-mistakes), and a merge decision computed from hard facts rather than the agent's opinion (marshal-factory). The recommended design is therefore a single marketplace plugin of roughly **7 skills, 8 agents, one `hooks.json`, and about 20 small scripts**, with all run state committed under `.factory/` in the target repo, stages dispatched as built-in subagents with explicit model tiers, and iteration caps enforced by scripts rather than prompts (Superpowers lost its five-round cap to post-compaction skill truncation and ran 18 fix rounds ([Superpowers release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md))). The research also argues for leaving most of the glamorous parts out of v1: parallel worktree implementers, Modal sandboxes, TestSprite, Mobbin, Figma, auto-merge and automatic learning all add cost or operational surface that the evidence does not yet justify for a solo developer on a Max subscription. Grill with Matt Pocock's 31-line `grilling` prompt plus Superpowers' hard approval gate (which cut spec-skipping from 24/24 runs to 3/24), verify with repo-native affected-only tests plus four free security scanners, review with three read-only lenses in parallel, and let GitHub CI remain the final validation. Build the v1 web-only pipeline first, measure a dozen runs, and only then add mobile capture, trackers and sandboxes.

## Thirty-three tools, three real factories, one reusable pattern

The catalogue below records what each resource does and how, its maturity as the notes recorded it (star counts were read from rendered GitHub pages because the API was blocked in every research session, so treat them as approximate), and a one-line verdict. The groups follow the brief. Where a verdict says "steal", the design in the next section says exactly where the piece lands.

## Claude Code's plugin rules shape every design choice

Several platform facts recorded in the notes decide what the plugin can and cannot do, so they come before the design. A plugin installs with `/plugin marketplace add owner/repo` then `/plugin install name@marketplace`, or in one shot with `claude plugin install name@marketplace --scope project`; committing the `enabledPlugins` entry in `.claude/settings.json` turns it on for collaborators but "doesn't download it to their machines", third-party marketplaces have auto-update **off by default**, cloud sessions "don't load the plugins you installed on your own machine", and there is **no install-time hook**, only `SessionStart` and a `Setup` event for `--init` in `-p` mode ([install](https://code.claude.com/docs/en/plugins/install); [hooks](https://code.claude.com/docs/en/hooks)). The manifest rules matter more than they look: `${CLAUDE_PLUGIN_ROOT}` is substituted inline in hook commands and in skill/agent Markdown but "the variables aren't present in the environment of commands Claude runs through the Bash tool", it changes on every plugin update so nothing may be stored there, and `${CLAUDE_PLUGIN_DATA}` is the only plugin-owned path that survives updates ([manifest reference](https://code.claude.com/docs/en/plugins/manifest-reference)). A `CLAUDE.md` at the plugin root is not loaded, plugins cannot ship `.claude/rules/`, a `bin/` directory blocks install on claude.ai and Cowork, and ECC's validator notes warn that declaring `agents` or `hooks` keys in `plugin.json` has caused rejections and "Duplicate hooks file detected" errors (the official docs describe both keys, so rely on auto-discovery of `skills/`, `agents/` and `hooks/hooks.json` and omit the keys) ([PLUGIN_SCHEMA_NOTES](https://github.com/affaan-m/ecc/blob/main/.claude-plugin/PLUGIN_SCHEMA_NOTES.md)).

Context behaviour constrains prompts. After compaction Claude Code re-attaches each invoked skill keeping only "the first 5,000 tokens of each" under a combined 25,000-token budget; Superpowers hit a 20,000-character cut-off and lost its loop cap, which is why loop caps must live in scripts and state files, not prose ([skills docs](https://code.claude.com/docs/en/skills); [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). The skill listing budget is 1% of the context window with each description truncated at 1,536 characters, so every factory skill except the two entry points should carry `disable-model-invocation: true` ("zero cost until invoked") ([features overview](https://code.claude.com/docs/en/features-overview)). SessionStart context never reaches subagents, and **plugin subagents ignore `hooks`, `mcpServers` and `permissionMode`**, so anything that must reach an implementer or reviewer goes through a plugin-level `SubagentStart` hook, as ponytail does ([sub-agents](https://code.claude.com/docs/en/sub-agents); [ponytail-subagent.js](https://github.com/dietrichgebert/ponytail/blob/main/hooks/ponytail-subagent.js)). Subagent frontmatter supports `model`, `tools`, `maxTurns`, `memory: project`, `isolation: worktree` and `effort`; concurrency is capped at 20 and spawn depth at 3; the official guidance to stay single-agent applies "when the task needs frequent back-and-forth, multiple phases share significant context, you're making a quick targeted change, or latency matters" ([sub-agents](https://code.claude.com/docs/en/sub-agents)).

Verification has hard edges. Claude Code's per-command Bash sandbox blocks Chromium (user namespaces), makes `localhost` private on Linux so commands cannot reach a dev server, needs `jest --no-watchman`, and is incompatible with `docker`; the docs say to run `--dangerously-skip-permissions` only inside a container, VM or the `srt` sandbox runtime ([sandboxing](https://code.claude.com/docs/en/sandboxing); [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Browser and simulator capture must therefore run with the sandbox excluded for those commands or inside `srt`/a dev container. On headless use, the notes record only fragments: `AskUserQuestion` "is absent" in `-p` mode, ponytail's band mod does not work under `claude -p`, Modal's Claude-Code-in-a-sandbox example authenticates with `ANTHROPIC_API_KEY` (API billing, not the Max subscription), and Archon supports `archon ai login anthropic` for Pro/Max accounts ([Modal example](https://modal.com/docs/examples/sandbox_agent); [Archon README](https://github.com/coleam00/archon/blob/dev/README.md)). Max-plan rate limits for unattended runs were covered in the earlier report and are not quantified in these notes; treat any assumption about sustained headless throughput on a subscription as unverified. One useful fact in the other direction: since v2.1.286 Claude runs a project skill named `verify` or `simplify` before commits, so a tiny `.claude/skills/verify/SKILL.md` pointing at the factory's verify script gets the gate for free even outside factory runs ([skills docs](https://code.claude.com/docs/en/skills)).

What the plugin writes into a target project, and what it never touches, is fixed by the platform facts above and by one rule the dry run forced: **no tracked file is written on the feature branch while a run is active.** Everything per-project lives in the repo under `.factory/`, but `.factory/runs/` is gitignored from the first commit (the dry run hit this four times: a tracked `state.json` blocked a branch switch, `evidence.json` and a `log.md` line made verify report its own bookkeeping as "dirty", and bookkeeping commits moved HEAD so the evidence SHA no longer matched). During a run the orchestrator logs to `runs/<id>/run.log`; at the end, `run-state.mjs snapshot` commits the run directory and the merged `log.md` onto the **base branch** through a temporary worktree, so the feature branch's HEAD, and the evidence pinned to it, never move. `verify.mjs` also excludes `.factory/` from its dirty check, except the recipe and scripts, which must be clean (and `trusted` proves the recipe equals the committed one). Three small files Claude Code already reads are written at setup, not during runs: the `CLAUDE.md` managed block, `.claude/rules/factory.md` and `.claude/skills/verify/SKILL.md`. Large or transient output (`runs/*/captures/`, `app-logs/`) is never committed. Nothing is stored under `${CLAUDE_PLUGIN_ROOT}`; the only plugin-owned writable path is `${CLAUDE_PLUGIN_DATA}` for caches such as downloaded scanner binaries.

### `/setup-factory`, step by step

The flow copies the shape the official new `/init` uses (explore with a subagent, ask the gaps, present a reviewable proposal, write on approval) and ECC's `project-init` contract ("Default to dry-run. Do not modify CLAUDE.md, settings files, rules, skills, or install state until the user approves") ([memory docs](https://code.claude.com/docs/en/memory); [project-init](https://github.com/affaan-m/ecc/blob/main/commands/project-init.md)).

First, detection runs as a script, not a prompt, because every input is a file-presence check. `detect-stack.mjs` reads the git remote and default branch, the lockfile (npm/pnpm/yarn/bun), monorepo signals (`pnpm-workspace.yaml`, `turbo.json`, `workspaces`), app indicators per package (`next.config.*`, `app.json`/`expo`, `nest-cli.json`, `vite.config.*`), `package.json` scripts named `test|lint|typecheck|build|e2e`, test configs (`vitest.config.*`, `jest.config.*`, `playwright.config.*`, `.maestro/`), existing `CLAUDE.md`/`AGENTS.md`/`.claude/rules/`, an existing `.factory/`, installed CLIs (`gh`, `playwright-cli`, `maestro`, `gitleaks`, `semgrep`, `osv-scanner`) and the output of `claude mcp list` for `linear`, `notion`, `figma`, `mobbin`, `playwright`, `TestSprite`. The indicator table is lifted from ECC's `config/project-stack-mappings.json` idea (per stack: `indicators`, candidate `commands.{build,test,lint}`) ([project-init](https://github.com/affaan-m/ecc/blob/main/commands/project-init.md)). Output is one JSON object printed to the skill.

Second, the skill asks, in mattpocock's setup style: "One section, one answer, then the next. Lead each section with the recommended answer so the user can accept it in a word" ([setup skill](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/SKILL.md)). The sections are (A) tracker: Linear if its MCP is connected, else local tickets; (B) docs: Notion if connected, else `.factory/specs/`; (C) apps: confirm each detected app's type (`web | mobile | backend | other`), its check commands, and the directories that hold its auth and data-access code (used by the review touch mask); (D) web runtime verification: `playwright-cli` if installed, else a one-line install hint, plus the `dev` command, port and health route for each web and API app; (E) mobile runtime verification: `mobile-mcp` (needs Xcode command line tools or `adb` and a simulator) and, if installed, Maestro for pinned flows; the simulator boot and app launch commands are proven in step three like any other check; (F) branching and merge policy: `git-flow` if a `develop` branch exists (recommended when it does), else `trunk`; the branch prefixes; merge method (`merge` for git flow, `squash` for trunk); and the merge policy `off | trial | auto`, recommended `trial`; (G) design sources: Figma and Mobbin only if their MCPs are connected; (H) security scanners: enable whichever are installed, recommend all four, and offer to write the starter `.factory/semgrep/` project rules for the detected frameworks; (I) previews: for each app, whether a host already deploys branches (detected from `vercel.json`/`.vercel`, `netlify.toml`, `wrangler.toml`, `railway.*`, `render.yaml`, `fly.toml`, `eas.json`, or a deployment status on the last PR), otherwise a custom command that prints a URL, otherwise local-only; (J) credentials: for each recipe `env` variable, a dev value for `.factory/env.local`, a per-run resource, or "not available"; (K) product analytics: for each app, the provider (detected from the SDK in `package.json`), the environment rule (which project or key each environment uses, and that dev and test never post to production), the capture method for verification (request interception by URL pattern, the SDK's debug log, or a local sink), the tracking-plan file if one exists, and whether consent gating applies. Nothing here asks about aesthetics, model names or token budgets; model tiers live in the plugin's defaults and can be overridden in `.factory/config.json` later.

Third, the recipe is proven, not guessed. For each app the skill runs every check command once (`setup`, `typecheck`, `lint`, `test`, `build`), records wall-clock seconds as a budget, and stops to ask if a command fails, which is exactly marshal-factory's onboarding rule ("runs the setup and every check until they pass") ([operations](https://github.com/ski043/marshal-factory/blob/main/docs/operations.md)). The result is `.factory/setup.json`, using marshal's schema (`runtimes`, `setup`, `checks.{test,lint,typecheck,build}`, `env` names with purposes but never values, `warmKey` globs) extended with `apps[]` and per-app `capture` commands:

The `preview` block is stack-agnostic by construction. `github-deployment` means "some host already builds this branch and posts a deployment"; the script does not care whether that host is Vercel, Netlify, Cloudflare Pages, Railway, Render or anything else, because all of them report through the same GitHub Deployments API. `command` covers hosts that do not (the EAS example above), `fixed` covers a shared staging service, and `local` is the fallback that always exists.

Fourth, the proposal. The skill prints the diff of every file it will create or change and waits. On approval `setup-factory.mjs --apply` writes: `.factory/{config.json, setup.json, index.md, log.md, lessons.md, tickets/, specs/, runs/, references/, knowledge/}`; a marker-managed block in `CLAUDE.md` (created if absent, never creating `AGENTS.md` when `CLAUDE.md` exists, per mattpocock) of at most six lines: a pointer to `.factory/index.md`, the non-obvious commands the recipe proved, and "run `/factory` for features and bugs"; `.claude/rules/factory.md` (under 40 lines: the four Karpathy rules, "stage outputs are files, never pasted", "never edit lint/CI/recipe config to make a check pass", "tests at pre-agreed seams only"); `.claude/skills/verify/SKILL.md` that calls `verify.mjs --fast`; `.gitignore` entries; a merged `.claude/settings.json` with `enabledPlugins`, `permissions.allow` for the plugin scripts, and `sandbox.excludedCommands` for `capture-web.sh`/`capture-mobile.sh` (so Chromium and `localhost` work); and, only for integrations chosen in step two, `.mcp.json` entries (`linear` → `https://mcp.linear.app/mcp` over HTTP as bmad's starter records, `figma` → `https://mcp.figma.com/mcp`, `mobbin` → `https://api.mobbin.com/mcp`, `TestSprite` → `npx @testsprite/testsprite-mcp@latest` with `API_KEY` from `userConfig`, marked `sensitive`) ([linear-ticketing.toml](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmad-agent-po/config/linear-ticketing.toml); [Figma install](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/); [Mobbin CLI](https://docs.mobbin.com/mcp/clients/claude-code-cli); [TestSprite install](https://docs.testsprite.com/mcp/getting-started/installation.md)). The whole write is idempotent: markers are replaced, existing hook and MCP entries are filtered by a `factory:` tag before re-append, as marshal's `install-target.ts` does ("Running it again changes nothing") ([install-target.ts](https://github.com/ski043/marshal-factory/blob/main/scripts/install-target.ts)).

For a new project the notes found no greenfield bootstrap in any repo; setup requires an initialised repo (a `package.json` is enough), and on an otherwise empty repo `/factory` routes the first request to a `build` whose first ticket is the scaffold.

### `/factory <prompt>`, stage by stage

The orchestrator is the `factory` skill running in the main session. It does three things only: route by reading small artifacts, dispatch stage subagents with explicit models, and call `run-state.mjs` to record progress. Every stage reads named input files and writes one named output file under `.factory/runs/<run-id>/`; nothing is pasted between stages (Superpowers: "a real session's dispatch hit 42k chars of which 99% was pasted history") ([SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). `run-state.mjs` is the only writer of `state.json` and the only place loop counters increment, so a cap that lives there survives compaction and cannot be argued with.

It also enforces one run at a time. `run-state.mjs init` writes `.factory/runs/ACTIVE` (run id, branch, session id, started-at) and refuses to start while that file names a run whose stage is not terminal, so two sessions cannot edit the same working tree; `/factory status` reads it, `/factory resume` continues it, and `/factory abandon <run>` clears it after confirmation, leaving the branch in place so a cleanup command never loses work. A stale lock, meaning the session is gone and the branch has not moved for longer than the run budget, is reported and offered for cleanup rather than overwritten. When runs are later parallelised through worktrees, the lock becomes per-worktree and nothing else changes.

Triage follows Archon's schema because it is the only design in the set that makes feature-vs-bug a judged field with a reason rather than a choice of entry point, and marshal's acceptance test decides the contract: "Write down the acceptance check, a test or an observable result, using only the issue text. If you cannot, the issue is ambiguous" ([triage block](https://github.com/coleam00/archon/blob/dev/.archon/workflows/sdlc/triage/archon-triage-block.yaml); [playbook](https://github.com/ski043/marshal-factory/blob/main/playbooks/factory.md)). Size masks stages the way ECC's tiers do: `s` with a derivable acceptance check takes the `oneshot` route (skip research and grilling, implement from `triage.md`, quick single-lens review), `m` runs the full flow with one ticket, `l` runs the full flow with multiple tickets ([orch-pipeline](https://github.com/affaan-m/ecc/blob/main/skills/orch-pipeline/SKILL.md)). A `bug` always starts implementation with a failing regression test committed on its own before the fix, which is marshal's and ECC's shared rule and the only part of TDD that is mandatory for the factory ([orch-fix-defect](https://github.com/affaan-m/ecc/blob/main/skills/orch-fix-defect/SKILL.md)).

Research runs before grilling, not after, because mattpocock's grilling rule is that facts are the agent's job and decisions are the human's; the researcher answers the factual half of the frontier so that rounds only contain decisions ([grilling](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)). The researcher's codebase half uses ECC's "Pattern Grounding" discipline ("If no similar code exists, state that explicitly. Do not invent a pattern") and `codebase-map.mjs` output rather than free grepping; its docs half reads the installed version from the lockfile for every package the change touches and fetches the official docs for that version with native `WebFetch`, because agent-reach adds nothing for public documentation and floorplan only covers the repo ([plan command](https://github.com/affaan-m/ecc/blob/main/commands/plan.md); [agent-reach skill](https://github.com/Panniantong/agent-reach/blob/main/agent_reach/skill/SKILL_en.md)). If a project already has a Context7-style docs MCP connected, the researcher uses it; the plugin does not bundle one.

Grilling is the one stage that cannot be a subagent, since subagents cannot talk to the user, and the notes support keeping it in the orchestrator: mattpocock's phase-boundary guidance says grilling and spec should share a context ("the implementation wants the reasoning verbatim"), and Superpowers found that "Look Before You Ask" and reading context first fixed the complaint that questions "got annoying fast and felt formulaic" ([PHASE-BOUNDARIES](https://github.com/mattpocock/skills/blob/main/skills/engineering/ask-matt/PHASE-BOUNDARIES.md); [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). The compromise that keeps the spec writer fresh is `grill.md`: after every round the orchestrator appends the settled `Q → A` pairs, spec-kit style (`## Clarifications / ### Session <date>`), so the spec subagent reads decisions from a file instead of inheriting the chat ([clarify](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)). Questions stay in plain chat; all three interview designs refuse `AskUserQuestion`, and mattpocock explains why ("Structured pickers push the model towards multiple-choice questions with pre-baked answers") ([native-question-tool](https://github.com/mattpocock/skills/blob/main/.out-of-scope/native-question-tool.md)). There is no question cap, by his argument, but the `s`-size route skips grilling entirely and the user can type "just go" at any round.

The spec template merges three sources: spec-kit's stable identifiers (`FR-###` requirements, `SC-###` measurable success criteria, prioritised user stories each with an independent test), mattpocock's `## Implementation Decisions` (no file paths), `## Testing Decisions` (named seams, ideally one) and `## Out of Scope`, and Superpowers' goals/non-goals/anti-goals plus "what's left to the builder" ([spec-template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md); [to-spec](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-spec/SKILL.md); [brainstorming](https://github.com/obra/superpowers/blob/main/skills/brainstorming/SKILL.md)). A one-line `surface: operate|persuade|read` field from impeccable tells the implementer whether restraint or expression is expected ([impeccable SKILL](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/SKILL.md)). After the spec is written, one builder-check subagent reads it cold and returns only "the questions you'd still need answered before you could plan this well", the orchestrator sorts them into answered/minor/theirs, asks the user the last group, and then the hard gate applies: nothing is built until the user approves the spec, the rule Superpowers measured from 24/24 skips to 3/24 ([builder-check](https://github.com/obra/superpowers/blob/main/skills/brainstorming/builder-check-prompt.md)).

Prioritisation produces tickets, not a plan. Each is a vertical slice "sized to fit in a single fresh context window", numbered in dependency order, with `Status:`, `Blocked by:` and acceptance-criteria checkboxes, and the user is quizzed on granularity and edges before anything runs ([to-tickets](https://github.com/mattpocock/skills/blob/main/skills/engineering/to-tickets/SKILL.md)). The frontier is a directory scan ("open, unblocked, and unclaimed; first by number wins") implemented in `run-state.mjs next-ticket` ([issue-tracker-local](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/issue-tracker-local.md)). The per-ticket plan is written just before implementation so it reflects code changed by earlier tickets, and it uses bmad's template with a `<frozen-after-approval>` intent block, a Code Map, Given/When/Then tasks, a `## Verification` section of commands with expected results, and Superpowers' `Interfaces: Consumes/Produces` block so an implementer that sees only its ticket still knows its neighbours' signatures ([plan-template](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmad-build/plan-template.md); [writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md)). bmad's size rule applies: "900–1600 tokens... above 1600 risks context-rot in implementation agents" ([workflow.md](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmad-build/workflow.md)).

### The implement → verify loop

The implementer dispatch is deliberately bare. bmad's wording is the model: "Read {plan_file} fully and implement it — the plan is the sole source of truth. Load every file listed in its frontmatter `context:` before you start", with the explicit prohibition on padding the dispatch with goal restatements or house rules ([step-03](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmad-build/step-03-implement.md)). The agent file carries the standing rules from Archon's `implement.md` ("Prose is a claim; the code is the fact"; install in locked mode; one commit per coherent outcome staged by name, never `git add -A`; "Check the code you changed, nothing more"; no speculative additions) and Superpowers' escalation statuses with "It is always OK to stop and say 'this is too hard for me.' Bad work is worse than no work" ([implement.md](https://github.com/coleam00/archon/blob/dev/.archon/workflows/sdlc/implement/commands/implement.md); [implementer-prompt](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/implementer-prompt.md)). The `ui-craft` or `ui-craft-expo` skill is preloaded only when the ticket touches a web or mobile app. Inside its turn the implementer runs `verify.mjs --fast` (affected typecheck, lint on changed files, `vitest run --changed <base>` / `jest --changedSince=<base>`), which the recipe budgets at about a minute; it never runs the full suite, following no-mistakes and Archon ("CI is the full validation") ([pipeline-steps](https://github.com/kunchenguid/no-mistakes/blob/main/docs/src/content/docs/reference/pipeline-steps.md); [Vitest CLI](https://vitest.dev/guide/cli.html); [Jest CLI](https://jestjs.io/docs/cli)).

When the implementer returns, the orchestrator runs `verify.mjs --full`, a script with marshal's `factory-verify` semantics: it runs every check in `setup.json` even after one fails, records `git rev-parse HEAD` and `git status --porcelain`, marks evidence `dirty` if the tree is unclean or HEAD moved during the run, marks it `untrusted` if any check command differs from the committed recipe, keeps the last 40 lines of each failure, and exits 0 only for a clean tree and all passes ([operations](https://github.com/ski043/marshal-factory/blob/main/docs/operations.md)). The agent then classifies the red into Archon's `red_cause` vocabulary: `introduced` or `incomplete` enters the fix loop; `inherited` (red on the base commit too) or `environment` (missing service, missing env) raises an attention item instead of burning rounds ([archon-implement](https://github.com/coleam00/archon/blob/dev/.archon/workflows/sdlc/implement/archon-implement.yaml)).

The loop cap is **three rounds**, chosen from the range the sources converge on (marshal and no-mistakes 3, ship-mate 2, Superpowers and Archon 5) and matching the "3 retries → escalate" rule in the diagram you saw. Round 1 and 2 resume the same implementer with the path to `evidence.json` and nothing else; round 3 dispatches a fresh implementer on the escalated model with "A prior implementer attempted this task 2 times; you own it now", which is Superpowers' rounds-4-5 tactic compressed ([fix-loop](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/fix-loop.md)). `run-state.mjs round implement` refuses to increment past the cap and returns `ESCALATE`, at which point the orchestrator writes an attention item and stops; ship-mate's "same blocker type twice ⇒ escalate immediately" rule short-circuits earlier when the failure signature repeats ([ship.md](https://github.com/wshobson/agents/blob/main/plugins/ship-mate/commands/ship.md)). Test integrity is enforced outside the model: the `guard-config.mjs` PreToolUse hook denies edits to lint/formatter configs, CI workflows, `package.json` scripts named in the recipe and `.factory/setup.json` while a run is active (ECC's `pre:config-protection`), and the reviewer's test-quality rule from no-mistakes ("the expected result must come from somewhere other than the code under test... the test should fail before the fix and pass after it") is a P1 finding, not a suggestion ([hooks.metadata](https://github.com/affaan-m/ecc/blob/main/hooks/hooks.metadata.json); [no-mistakes skill](https://github.com/kunchenguid/no-mistakes/blob/main/skills/no-mistakes/SKILL.md)).

### Runtime verification: run every app, walk every criterion

Static checks and unit tests prove that code compiles and that functions return what their tests expect. They do not prove that the feature works when a person uses it, so every run also starts the applications and exercises the change the way a user would, and the result is evidence in the same sense as the test output: per success criterion, with captures, pinned to the commit.

`run-apps.sh up --profile <name>` starts every app listed in `setup.json` on the run's branch under a named environment profile: `setup.json.profiles` declares `default` plus variants (a tight rate limit, a file store, the API stopped, analytics unset) as per-app environment overrides, `app: null` means "do not start this app", and each success criterion in the spec is tagged with the profile it needs so `qa` can sequence its walk by profile instead of marking criteria `blocked: environment`; the dry run needed four such variants and had to run them by hand before this existed, and the five profiles were then proven end to end (third request 429 with `Retry-After: 3` under the tight limit, a 111-byte data file under the file store, 502 through the proxy with the API down, an empty analytics URL in the served module). Dev servers get run-scoped ports and a run-scoped database URL from the recipe's `env` list; mobile gets a booted simulator or emulator with the app launched (`xcrun simctl boot` + the Expo dev client, or `adb` on Android). `up` health-checks each app (an HTTP probe for web and API, the app's foreground state for mobile), writes `apps.json` with URLs, device ids and the profile's environment, and `down` kills by port rather than by pid, because a pnpm wrapper's node child is reparented to PID 1 when the wrapper dies and a pid-based kill leaks it (the dry run's first `down` left the old API running and the "fresh" store was not fresh). These commands live in `sandbox.excludedCommands`, because Claude Code's Bash sandbox blocks Chromium and makes `localhost` private, and because a simulator is an OS-level process ([sandboxing](https://code.claude.com/docs/en/sandboxing)). iOS requires macOS; on a Linux host the mobile app is verified on Android only and `qa.json` says so. Pinning flows as scripts happens after `down`, because the project's Playwright config starts its own servers and refuses to reuse running ones.

The `qa` agent is a fresh sonnet subagent with no `Edit` or `Write`, so it cannot repair what it finds; it can only report. Beside its per-criterion before/after captures, `capture-states.mjs` captures a named state list from the plan (empty form in both schemes and at phone and desktop widths, button focus, invalid-input and API-error states in dark mode, the loading placeholder reached through a delayed route, the returning-visitor reload), so the UI reviewer judges every state the spec describes and not only the ones a criterion happens to pass through. Two capture rules came out of the dry run: screenshots are taken with animations settled (`animations: "disabled"` plus a short wait), because a card captured mid-fade looked like a dark-mode contrast failure that did not exist; and the browser context grants clipboard permission, because without it every "Copied" capture showed the clipboard-denied fallback and the UI reviewer, correctly, refused to judge it and asked for a recapture. It reads the spec's `SC-###` list and the plan's routes and screens, and for each criterion it performs the steps a user would and records a before and after capture plus a one-line verdict. It drives the apps through the cheapest driver that can see what it needs, in this order: `playwright-cli` for web, which works from accessibility snapshots and costs no screenshot tokens for ordinary flows ([playwright-cli](https://github.com/microsoft/playwright-cli)); `mobile-mcp` for mobile, which exposes `mobile_list_elements_on_screen`, `mobile_click_on_screen_at_coordinates`, `mobile_swipe_on_screen`, `mobile_type_keys` and `mobile_take_screenshot` against iOS simulators, Android emulators and real devices, installs with `claude mcp add mobile-mcp -- npx -y @mobilenext/mobile-mcp@latest`, and needs only Xcode command line tools or `adb` rather than Java ([mobile-mcp](https://github.com/mobile-next/mobile-mcp)); and screenshot-driven interaction ("computer use" in the practical sense: look at a picture, click a coordinate) only when the element tree cannot see what the criterion is about, such as a canvas, a chart, a native permission dialog, a visual state like "the row turns green", or a layout judgement. For web that is Playwright MCP's `--caps=vision` or `playwright-cli`'s screenshot plus coordinate click; for mobile it is `mobile-mcp`'s coordinate tools on a screenshot ([playwright-mcp](https://github.com/microsoft/playwright-mcp)). There is no OS-level computer-use tool inside Claude Code itself; the desktop app's computer use is not callable from a pipeline, so "computer use" here means these MCP servers, which is also what keeps the factory stack-agnostic: anything that can be shown on a screen can be driven.

The expensive part is bounded in three ways. First, a screenshot budget: `config.qa.screenshots_max` (default 40 per run) and `maxTurns` on the agent, enforced by the agent's frontmatter and counted in `qa.json`; when the budget runs out the remaining criteria are `blocked: budget` rather than silently skipped. Second, the escalation order above, so the vision path is the exception rather than the default. Third, pinning: every flow the agent walked successfully is written back as a script, a Playwright spec under `tests/e2e/<ticket>.spec.ts` for web and a Maestro flow under `.maestro/<ticket>.yaml` for mobile, generated from the actions it took (Playwright's own generator agent does this for web; for mobile the agent writes YAML from the element ids it tapped) ([Playwright test agents](https://playwright.dev/docs/test-agents); [Maestro](https://github.com/mobile-dev-inc/maestro)). On the next run those scripts are part of `verify.mjs --full` and cost no tokens, and the `qa` agent only walks criteria that have no pinned script yet. This is the "explore with vision, pin with a script" pattern, and it is the reason runtime verification gets cheaper per run rather than more expensive.

`qa.json` feeds the loop like any other evidence: a `fail` on any criterion enters the implement → verify loop with the criterion, the steps taken and the two captures (the implementer sees what the user saw, not a description of it); a `blocked` with an `environment` cause raises an attention item; and `merge-decision.mjs` requires every `SC-###` to be `pass` with evidence before it will say `merge`. The UI reviewer is unchanged and deliberately separate: `qa` answers "does it work", using captures it produced by exercising the feature, while the UI reviewer answers "is it right", judging those same captures against the spec and the design floor without a browser. Keeping them apart preserves the rule that the agent that produced the evidence is not the one grading it.

Benefits: the factory proves the feature from the user's side on every run, for web, mobile and backend alike (backend criteria are walked through the web or mobile app, or through `curl` against the running API when the criterion is an API response); it needs no `testID` instrumentation to get started; and it leaves behind regression tests. Tradeoffs: screenshot-driven steps cost roughly a thousand tokens each plus reasoning, so an unbounded vision walk is the single most expensive thing the pipeline can do, which is why the budget and the driver order exist; vision runs are not deterministic and never serve as the regression gate, only the pinned scripts do; a flaky dev server or a slow simulator boot shows up as `blocked`, so the recipe's `dev` commands and health probes have to be as proven as the check commands; and running every app per run adds minutes, which is acceptable for a factory that runs one feature at a time but is the first thing to revisit if runs are ever parallelised.

### Product analytics as a verified requirement

Analytics instrumentation is part of what a feature is, so it is specified, implemented and verified like any other requirement rather than remembered afterwards. The spec template gains an `## Analytics` section: for each user-visible behaviour, the event name, its properties with types, the trigger ("fires once when the export completes, not on click"), and the success metric the feature exists to move. The grilling frontier includes "how will you know this worked?" so the section is filled by a decision, not invented by the spec writer. Each analytics line maps to a success criterion (`SC-###`) in the same way UI behaviour does.

Event names and properties live in a tracking plan, `.factory/knowledge/tracking-plan.md` (or the project's existing one, recorded at setup), which is the analytics equivalent of the API contract: the planner adds new events there as a task, and `contract-diff.sh` treats a renamed or removed event, or a changed property type, as a breaking change in `contract.json`, because dashboards and downstream tools depend on those names the way mobile builds depend on API shapes. The implementer follows the project's existing SDK and naming convention (setup records the provider per app from the SDK in `package.json`; nothing is assumed about which one) and the environment rule from setup section K, which exists for one reason: dev, test and preview must never post to the production project.

Verification is evidence, not trust. While the `qa` agent walks each criterion, the capture scripts record what the app actually sent: for web, `playwright-cli` intercepts requests matching the provider's endpoint pattern (or the SDK's debug output) and writes them to `analytics.json`; for mobile, the SDK's debug logging is collected through `mobile-mcp`'s log tools, or the simulator is pointed at a local sink that records payloads. `verify.mjs` then compares expected events from the spec with observed ones and records per event `fired | missing | extra | wrong_properties`, and the result is a `qa.json` criterion like any other, so a missing event enters the fix loop with the capture that shows it missing. Three further checks ride on the same data: no PII in event properties (an email, a name or a free-text field is a `P1` for the security lens); when setup recorded consent gating, no analytics request may be observed before consent is given in the walk, which is a `P0` for an EU product; and no request to a production analytics key from a non-production build, a `P0` regardless of market.

Benefit: analytics stops being the thing that is discovered missing in the dashboard a week after launch, and the consent and environment checks are the ones that are expensive to get wrong in the EU. Tradeoff: it adds a section to the spec and a line per event to the plan on every feature, so the triage route `oneshot` skips it unless the ticket is explicitly about analytics; interception is provider-specific in one place (the endpoint pattern recorded at setup), and a provider that batches or samples events needs the SDK's debug mode rather than request capture, which setup proves once like any other check.

### The trust boundary: who may read untrusted input

The factory takes text from places it does not control: tracker issues, web pages fetched for package documentation, Notion pages, Mobbin and Figma content. Any of them can carry instructions aimed at the agent, and the earlier report's incidents (a malicious GitHub issue leaking private data, the Cline publish-token theft) all began that way. The design was already mostly safe by construction, because the researcher is read-only and the implementer never fetches, but that was a coincidence of the stage layout rather than a rule. It is now a rule, written in `.claude/rules/factory.md` and in each agent file.

Only `triager` and `researcher` read untrusted input. Both are read-only, have no Bash beyond `git log`, and can only produce a file. Everything that can act, meaning the implementer with Edit, Write and Bash and the `qa` agent with a browser and a simulator, reads only artifacts the factory itself wrote: `plan.md`, `spec.md`, the ticket, `evidence.json`. Fetched content never reaches them raw; it reaches them as the researcher's summary in `research.md`, which the planner has already read and turned into a plan. The researcher's prompt labels every fetched page as data, quotes facts with their URLs, and is told that instructions found inside a page or an issue are facts about that page, never directions to follow; `research.md`'s 300-line cap also bounds how much injected text could ride along. The `guard-paths.mjs` PreToolUse hook confines every Write, Edit and shell write (redirects, `tee`, `cp`/`mv`/`rm` targets) to the worktree, with `/dev/` and `/tmp/` allowed, and during an active run also denies edits to CI workflows, lint config, the recipe, the factory scripts and agents, and `.claude/`, so an injected instruction cannot rewrite the rules that constrain it. It was written after a dry-run implementer's replay script dropped a log file at the filesystem root, and it is unit-tested against that exact command and eleven others (deny `> /srv.log`, deny `tee ~/x.txt`, deny `cp dist/app /usr/local/bin/app`, deny `sed -i` on the recipe; allow in-repo redirects, `/dev/null`, `/tmp` scratch). Secrets stay out of reach by the earlier report's `.env*` read block and by the run-scoped environment carrying only the dev or branch credentials the recipe lists. This is Simon Willison's "lethal trifecta" applied stage by stage: no single agent holds untrusted content, private data and the ability to act at the same time ([lethal trifecta](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)).

Benefit: the two agents that can take actions never see untrusted text, which is the whole defence; everything else is depth. Tradeoff: the implementer cannot look something up mid-task. When it hits a gap it returns `NEEDS_CONTEXT` with the question, and the orchestrator dispatches the researcher once for that question and resumes the implementer with the answer in a file, which costs one dispatch but keeps the boundary intact.

### Credentials: the run's environment is the recipe's environment

The implementer and the `qa` agent run real processes: integration tests against a database, dev servers that call external services, a mobile app talking to an API. Whatever those processes can read, an agent with Bash can print, so the `.env*` read block from the earlier report is a guardrail and not a boundary. The boundary is that a run never inherits the developer's shell environment at all. `run-apps.sh` and `verify.mjs` build the process environment from one file, `.factory/env.local` (gitignored, created by setup), and nothing else; an agent that runs `echo $DATABASE_URL` gets the dev value because that is the only value present.

Setup section J fills that file. For every variable in `setup.json.env` it asks where the factory's value comes from: a dev value entered once and stored in `.factory/env.local`; a resource created per run (a Neon or Supabase branch, v2); or "not available to the factory", in which case the checks that need it are recorded as `skipped` in `evidence.json` and the merge rule reports a skipped required check as `needs-human`, which is the honest state rather than a green that proves nothing. Production values are not offered as an option in that prompt. Third-party services get test-mode or sandbox credentials (Stripe test mode, a sandbox OAuth application) or a local mock, and the `network` touch makes the security reviewer confirm that no new external call from a test points at a live endpoint. `gh` is the one real credential the factory needs: a fine-grained token scoped to the repository with contents and pull-requests write, no administration and no `workflow` scope so an agent cannot change CI, stored in the factory's own configuration rather than the developer's global `gh auth` ([fine-grained tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)). Branch protection on `main` and `develop` is what enforces "no merge outside the rule"; the hooks only keep an agent from trying. Previews run on the host with the host's environment and the factory only reads their URLs, so nothing changes there. Benefit: a confused or compromised agent can at worst break a dev database and open a PR; it cannot reach production data, production keys or CI. Tradeoff: one more setup section, and a service you will not give the factory turns its checks into `skipped` rather than green.

### Budgets, failure and recovery

Round caps bound how many times the loop may try; they do not bound what a single attempt may cost, and on a subscription the cost that bites is the usage window. The budget scales with the work: `tokens_overhead` (default 700k, for triage, research, spec, tickets, review and PR) plus `tokens_per_ticket` (default 700k) times the ticket count, and the same shape for minutes (`minutes_per_run` plus `minutes_per_ticket`); until the ticket count is known the fallback `tokens_per_run` applies. The defaults are calibrated to the first dry run (3.33M tokens for four tickets; a flat 2.25M cap had fired after review, a false stop) and are meant to be re-tuned from the golden scorecard. Every subagent return reports its usage; the orchestrator calls `run-state.mjs spend <stage> <tokens>` after each dispatch, which records spend per stage in `state.json` and refuses the next dispatch once a budget is crossed, returning `BUDGET` so the run ends as `needs-human` with a breakdown instead of an unexplained stop. At 70% the orchestrator warns and asks whether to continue. Budgets are checked only at dispatch boundaries; they never kill an in-flight subagent, whose own `maxTurns` is the mid-flight bound. Scripts cost nothing and are not counted. Each run's totals go to `log.md` as one line, which is the data every later decision in the build order depends on. One limit to state plainly: the token counts subagents report include each turn's fixed system-prompt and tool-schema cost, so they are reliable as relative measures between runs rather than as a bill, and they explain why even a three-tool-call haiku dispatch costs six figures.

Recovery rests on the fact that the factory keeps no state in conversation. Every stage leaves a file, every implementer step leaves a commit, and `run-state.mjs dispatch` records the stage, the SHA and, once known, the agent id *before* the subagent starts. Recovering therefore means reading the disk and continuing from the last checkpoint, never reconstructing what an agent was thinking. Four habits make that cheap and are rules in the agent files: the implementer commits per coherent outcome and appends to `implementation.md` as it goes rather than at the end (Superpowers' progress ledger exists because "controllers that lost their place have re-dispatched entire completed task sequences" ([SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md))); the `qa` agent writes `qa.json` per criterion as it walks, so an interruption leaves "SC-1 pass, SC-2 pass, SC-3 blocked: interrupted"; a return without the required status line is `INCOMPLETE`, never done; and the code reviewer flags an implementer that returned with a single giant commit, because that is the habit failing.

The platform's own behaviour fits this. A subagent that reaches `maxTurns` returns its output marked partial (v2.1.246+) and can be resumed with its full history; a subagent cut off by a rate limit, overload or server error returns its partial output with a note if it had produced text, or fails with "Agent terminated early due to an API error" if it had not; a background subagent is marked failed with its last output attached; and a subagent can be resumed by id after restarting Claude Code by resuming the same session ([sub-agents](https://code.claude.com/docs/en/sub-agents)). Each subagent also has its own context window sized by its model and auto-compacts; `autoCompactWindow` (v2.1.296+) is set on the implementer so compaction happens with headroom, and the 900–1,600-token plan and one-window tickets keep implementers far from the wall in the first place.

What fails, and what happens:

| Failure | Recovery | Human involved |
|---|---|---|
| Tests red, review findings, a `qa` criterion fails | The loop: failure plus evidence files go to the implementer; `red_cause` decides whether it counts as a round; caps of 3 and 2; same failure signature twice ends early | Only at the cap |
| Dev server, simulator or database will not come up; base branch already red | `environment` or `inherited`, not a round; `run-apps.sh` retries once, then an attention item with the command and its last 40 lines | After one retry |
| Subagent stops early (`maxTurns`, cut-off, API error, usage window) | Resume the same agent by id when it returned partial output; fresh dispatch from git state when it produced nothing; a usage-limit stop is recorded as `suspended`, never as a round | Only if it repeats |
| Session dies (crash, closed laptop, killed terminal) | `/factory resume` runs the reconcile protocol below | One command |
| Default branch moved | Rebase before review, one catch-up before merge; conflicts always escalate | On conflict |
| Implementer finds the plan wrong | `BLOCKED: bad_plan` → revert the ticket's commits, planner amends once, re-implement (a round); `BLOCKED: intent_gap` → stop, since only the human may change the spec's frozen intent (bmad's routes) | On intent gaps |
| Implementer needs information | `NEEDS_CONTEXT` → one researcher dispatch for that question, implementer resumed with the answer as a file | No |
| Budget exhausted | `needs-human` with spend by stage; resume after raising the budget or splitting the ticket | Yes |
| Ticket 2 of 4 fails | Ticket 1's commits stay; the escalation says "1 done, 2 blocked, 3–4 not started"; options are fix by hand, `--skip-ticket 02` (status `dropped`), or `replan 02` | Yes |
| The factory itself breaks (script crash, malformed artifact, missing status line) | Fail closed: `INCOMPLETE`; attention item says "factory error" rather than guessing | Yes |
| External call fails (`gh`, an MCP server, a docs fetch) | Typed errors in agent-reach's style: `RATE_LIMITED` waits once; `NEED_SETUP` and `UPSTREAM_BROKEN` escalate at once; nothing retries in a loop ([agent-reach](https://github.com/Panniantong/agent-reach/blob/main/agent_reach/skill/SKILL_en.md)) | Sometimes |
| Merged and main goes red (`auto` mode, v3) | Watch main for 60 minutes; open a revert PR | Merges the revert |

The reconcile protocol is `run-state.mjs reconcile`, and it is what `/factory resume` and every "fresh dispatch" above actually run. First, read `ACTIVE` and `state.json`: which stage was dispatched, at which SHA, with which agent id, and why it stopped. Second, clean up: `run-apps.sh down` (idempotent) kills stale dev servers and simulators, and any uncommitted changes left by a dead implementer are committed as `wip(factory): salvaged from round N`, so they are visible and evaluable rather than lost or silently kept. Third, reconcile stages: a stage whose output file exists and is marked done is skipped and never re-run; the stage marked dispatched with no output is the one to continue, by resuming its agent if the stop was partial or cut-off, or by a fresh dispatch that points at the git log since the dispatch SHA and at `implementation.md`. Fourth, `verify.mjs --fast`, so the continuation starts from known state rather than from the last agent's claim. Fifth, continue from the frontier; completed tickets are already committed and skipped. An attempt counts as a round only if it produced commits, so an API error that produced nothing costs nothing against the cap. Reviewers are the exception to resumption: a cut-off review is re-run fresh, never resumed, so a half-formed verdict cannot anchor the second attempt.

What stays human is deliberate: merge conflicts, intent gaps, P0 security findings, budget exhaustion, environment failures after one retry, and factory bugs. Each is a decision made with partial context or a repair that could hide a real problem, and the factory's trustworthiness depends on it not guessing at those. Every escalation is one attention item in one format, Archon's and marshal's: what happened, the evidence paths, a recommendation, and two or three options as runnable commands. Benefit of the whole model: nothing built is ever lost and resumption is one command. Tradeoff: it holds only if agents actually commit as they go and write their reports progressively, which is why those are enforced rules rather than advice.

### Golden tasks: the pipeline's own regression suite

Every edit to a skill, an agent prompt, a cap or a model tier changes the pipeline's behaviour, and without a fixed comparison the only way to notice a regression is in real runs, later. Superpowers could remove its review loops with confidence only because it ran the same tasks across versions and compared scores ([release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). The `evals/` directory tests each stage prompt in isolation; `golden/` tests the whole thing end to end.

`golden/fixture/` is a minimal monorepo with a Next.js app, a Nest API and an Expo app, each with a few routes and tests, and with both `main` and `develop` branches so the branching logic is exercised. Six tasks sit beside it, each with a `task.md` prompt, a `grill-answers.md` that answers the interview headlessly, and an `expected.json`: the triage verdict (type, size, route, lane), which stages must run and which must be skipped, the `SC-###` list the spec must contain, which test files must exist afterwards, the target branch of the PR, and that the P0 count is zero. The six are a `feature` touching all three apps, a `bug` with a planted regression on `develop`, a `hotfix` with a planted regression reported against a release (expected: branch from `main`, PR to `main`, back-merge PR to `develop`), a `refactor`, an `s`-size oneshot, and a deliberately ambiguous request whose expected outcome is `NEEDS_CLARIFICATION` with no branch created. `factory golden` runs them with `claude -p` against a fresh clone of the fixture and writes `golden/scorecard.json`: outcome match per task, rounds used, tokens and minutes per stage, compared with the committed previous scorecard, with a non-zero exit on any outcome mismatch or a cost increase above a configurable percentage.

It is a pre-release check, not a pre-commit one. Six end-to-end runs plausibly cost 2–4M tokens and 30–60 minutes, and headless runs draw from the subscription's window, so it runs before a plugin version is tagged and when the window is fresh. The ambiguous task is the one to keep if the rest is ever trimmed, because "refuses to build from a bad spec" is the behaviour that erodes first when prompts are tuned for throughput. Benefit: prompt changes are made with evidence, and the scorecard is the cost baseline the build order keeps asking for. Tradeoff: the fixture has to be maintained alongside the plugin, and a scorecard from a toy repo does not predict costs on a real one; it predicts direction, not magnitude.

### Notifications: GitHub is the inbox

Three events need a human: a run needs you, a run delivered a PR, a run failed, plus the 70% budget warning. In v1 all of them surface through GitHub and nothing else. A `needs-human` run opens a draft PR labelled `needs-human` with the attention item (what happened, evidence paths, recommendation, runnable options) as its first comment; a delivered run opens the PR with the evidence table, captures and the two-minute verification; a failed run with a branch does the same as `needs-human`, and one without a branch posts the attention item as a comment on the tracker issue when there is one, otherwise only to `log.md`. GitHub's own notifications carry these to wherever you already read them, and `/factory status` plus `log.md` give the local view. `config.notify` exists as an empty hook point so a webhook target (Slack or anything else) can be added later by one script without touching the orchestrator; Slack was considered and deferred, because the official Claude-in-Slack integration already starts cloud sessions from a mention and loads the repo's committed skills, so "@Claude run `/factory resume`" will work there without the factory knowing Slack exists, and a one-way webhook adds little over GitHub's notifications for a single developer. Per-stage notifications are deliberately absent; they are noise within a day.

### Branching: git flow, chosen by triage

The factory follows git flow when the project does: `main` is production, `develop` is integration, work happens on prefixed branches, and the branch's base and the PR's target depend on what the work is ([git flow](https://nvie.com/posts/a-successful-git-branching-model/)). Setup detects a `develop` branch and proposes `git-flow`, otherwise `trunk`; the branch names and prefixes are configuration, not assumptions.

Triage decides the lane, which is why the branch is created after triage rather than at run start. `feature`, `refactor`, `maintenance` and `docs` become `feature/<key>-<slug>` from `develop` with a PR to `develop`. A `bug` becomes `bugfix/<key>-<slug>` from `develop`, unless triage marks it `in_production: true` (the issue references a released version, or the user says so in grilling), in which case it becomes `hotfix/<key>-<slug>` from `main` with a PR to `main`. Triage records `base_branch` and `target_branch` in `triage.md`, `run-state.mjs init` stores them with the `base_sha`, and every later step reads them: `verify.mjs` substitutes `{base}` in the recipe's affected-test commands with the run's base, `sync-base.sh` rebases onto that base rather than onto a fixed default, `review-package.sh` diffs against it, and `merge-decision.mjs` checks the PR targets it. Branches carry no `factory/` prefix; the factory identifies its work with a `factory` label and the run id in the PR body, so the branch list reads like human work and existing branch-protection rulesets apply unchanged.

Two git-flow rules fall on the merge step. The merge method defaults to a merge commit (`gh pr merge --merge`, git flow's `--no-ff`) so a feature's commits stay grouped in history; `squash` is available for projects that prefer it, and trunk mode defaults to `squash`. A hotfix merged to `main` is not finished until it is also in `develop`, so after a hotfix merge the orchestrator opens a second PR, `develop ← hotfix/<key>-<slug>`, with a body that says it is a back-merge and no review loop; a back-merge conflict escalates like any other. The factory never creates `release/*` branches or tags in v1; cutting a release is a human or CI decision, and a `/factory release` skill is a v3 question. Benefit: the factory's PRs land where a human's would, previews map cleanly (feature branches get preview deployments, `develop` is staging, `main` is production), and hotfixes cannot be lost on the next release. Tradeoff: git flow adds a second integration branch to keep green, so the `inherited` red-cause check runs against `develop` for most runs and against `main` for hotfixes, and a red `develop` blocks features until someone fixes it, which is the model working as intended.

### Rebase before review, catch up before merge

The run branches from `base_sha` on its base branch, so if that branch moves during implementation every later fact describes a tree that will never exist after merge. no-mistakes rebases as its second step for this reason ([pipeline-steps](https://github.com/kunchenguid/no-mistakes/blob/main/docs/src/content/docs/reference/pipeline-steps.md)). `sync-base.sh` runs at two points. Before review, while the PR is still unopened and history can be rewritten freely, it runs `git fetch origin && git rebase origin/<base_branch>`; since every SHA changes, `verify.mjs --full` runs again and `review.diff` is computed from the new merge base. At the merge decision, `merge-decision.mjs` reports `behind_base: true` whenever the default branch has moved since the evaluated head and refuses `merge`; in `auto` mode the orchestrator does one catch-up with `gh pr update-branch` (a merge, not a rebase, so the open PR's commits and the evidence pinned to them stay intact), re-runs verify, and re-evaluates once; in `trial` and `off` it reports the fact and stops ([gh pr update-branch](https://cli.github.com/manual/gh_pr_update-branch)).

Conflicts always escalate. A rebase or update that conflicts ends the run with a `needs-human` attention item naming the files, and the script aborts the rebase so the branch is left as it was. The alternative, letting the implementer resolve conflicts confined to its own Code Map in one bounded round, was considered and left out of v1: an agent choosing between two versions of a file with partial context is how a merged main quietly loses someone else's change, and for a developer working one feature at a time conflicts should be rare enough that handling them by hand costs less than the risk.

### The review stage: three read-only lenses, one synthesis

Review runs only when `evidence.json` is green, because reviewing red code wastes the expensive model. `review-package.sh` writes `review.diff` from the `base_sha` recorded before dispatch (never `HEAD~1`, which "silently drops all but the last commit") with `-U10` context, commits and files-changed sections ([review-package](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/scripts/review-package)). Three subagents then run in parallel, all read-only, all told to read the diff file once and not crawl the codebase, all returning findings in one schema: `id`, `severity P0|P1|P2|P3`, `action fix|ask|note` (a missing action is treated as `ask`, no-mistakes' fail-closed rule), `location` (`file:line` or `capture:region`), `claim`, `evidence`, `fix`, plus a closing `verdict: approve | needs-fixes | block` ([auto-fix](https://github.com/kunchenguid/no-mistakes/blob/main/docs/src/content/docs/concepts/auto-fix.md)). Severity semantics are impeccable's: P0 blocks the task, P1 "would a user contact support about this?", P2 has a workaround, P3 polish, and "Keep P3s few" ([critique](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/reference/critique.md)).

The **code reviewer** (opus, `memory: project` so it remembers repo-specific false positives) covers mattpocock's two axes in one agent, as Superpowers settled on after finding two reviewers per task "expensive and easy to game": spec compliance (missing, extra/scope creep, misunderstood, quoting the spec line) and standards (the Fowler smell baseline where "a documented repo standard always wins"), with Superpowers' "Do Not Trust the Report" rule that the implementer's rationale never downgrades a finding, and no-mistakes' Simplification pass that reports any component "not strictly required to satisfy that intent" as a `P2 ask` ([code-review](https://github.com/mattpocock/skills/blob/main/skills/engineering/code-review/SKILL.md); [task-reviewer-prompt](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/task-reviewer-prompt.md); [pipeline-steps](https://github.com/kunchenguid/no-mistakes/blob/main/docs/src/content/docs/reference/pipeline-steps.md)).

The **UI/UX reviewer** carries a quality bar, not only a fidelity check, because the dry run shipped a functional but generic card after the lens had correctly found its three defects and filed them as P2s that never loop. Three mechanisms fix that: the `ui-craft` skill loads the project's `DESIGN.md` tokens and a short craft floor at implementation time (one primary action per surface, full-width link values that never clip, reserved widths so label changes do not shift layout, `:focus-visible` styles that do not imitate inputs, ≥ 44 px tap targets, contrast ≥ 4.5:1, transitions ≤ 300 ms ease-out, no `scale(0)`), which the dry run's UI fix round followed with measured results (0 px Copy→Copied shift, 7.9:1 and 8.0:1 contrast, 16 px spacing); the lens runs impeccable's critique rubric with a numeric floor; and, by the synthesis rule above, a `disposition: fix` on a `persuade` or `operate` surface is an open P1 that enters the fix loop and is closed only by a UI re-review that says `ship` (the dry run's re-review did exactly that: four resolutions with the capture that shows each, two new P3s, `disposition: ship`). It runs only when the diff touches UI files (`.tsx`, `.jsx`, `.css`, Expo screens) and only after `capture-web.sh` has produced evidence: `playwright-cli` opens the dev server headless, visits the routes the plan names, and saves `captures/<route>-<width>-<scheme>.png` at 390, 768 and 1440 in light and dark plus `console.json`; for mobile (v2) `capture-mobile.sh` runs a Maestro flow and `xcrun simctl io booted screenshot` / `adb exec-out screencap -p` in light, dark and `font_scale 1.3` ([playwright-cli](https://github.com/microsoft/playwright-cli); [ios.md](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/reference/ios.md); [android.md](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/reference/android.md)). The agent is impeccable's finish-reviewer reshaped around a spec: check 0 verifies every required capture exists and is not blank, else it returns `disposition: recapture` and stops ("a verdict derived from a broken capture launders the breakage into an approval"); it inventories the spec's acceptance criteria and, when present, the Figma `get_screenshot` cached at plan time, before reading the implementer's summary; it classifies every salient element `match | acceptable adaptation (cited) | missing | contradicted | added without approval`; and its first line is one of `recapture | rebuild | fix | ship` ([finish-reviewer](https://github.com/pbakaus/impeccable/blob/main/.claude/agents/impeccable-finish-reviewer.md)). Two sub-passes add behaviour to looks: emilkowalski's `break-ui` (a field table from the spec's data model with limits from Zod or migrations, a worst-case fixture, a Broken/Ugly/Fragile table with `file:line`) and a trimmed animation check against his ten standards with a Before/After/Why table ([break-ui](https://github.com/emilkowalski/skills/blob/main/skills/break-ui/SKILL.md); [review-animations](https://github.com/emilkowalski/skills/blob/main/skills/review-animations/SKILL.md)). The agent has no browser and edits nothing; it judges pictures and the spec, taste-skill's rule that "you wrote the code, so you will read your intentions into it" ([taste critique](https://github.com/Leonxlnx/taste-skill/blob/main/skills/taste-skill/references/critique.md)). If `npx impeccable detect <url> --json` is installed, its deterministic findings are run by the script and handed to the reviewer as a separate file after the visual pass, mirroring impeccable's isolation rule that detector output "anchors judgment" ([impeccable critique](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/reference/critique.md)).

The **security auditor** is mostly a script. `security-scan.sh` runs `gitleaks git --no-banner --redact --report-format json` scoped to the branch, `npm audit --audit-level=high --omit=dev --json` (or the pnpm/yarn equivalent, unverified in the notes), `osv-scanner scan source -r .`, and `semgrep scan --config auto --error --metrics=off --baseline-commit $(git merge-base HEAD origin/main) --json`, merging them into `security.json`; all four are free, diff-aware or exit-code gated, and run offline except for vulnerability lookups ([gitleaks](https://github.com/gitleaks/gitleaks); [semgrep CLI](https://docs.semgrep.dev/cli-reference); [OSV](https://google.github.io/osv-scanner/usage/scan-source/); [npm audit](https://docs.npmjs.com/cli/v10/commands/npm-audit)). The sonnet agent then reads `security.json` and the diff with one job: trace authorization and privacy paths whenever the change touches auth, tokens, sessions, PII, payments, CORS, migrations or external calls, which is no-mistakes' review rule and ship-mate's halt list; any such touch without a corresponding test is a `P1 ask` ([ship-mate review](https://github.com/wshobson/agents/blob/main/plugins/ship-mate/agents/review.md)). wshobson's note that the `fable` tier's safety classifiers "fall back to Opus on that content anyway" is one more reason to keep this lens on a mid-tier model ([docs/agents.md](https://github.com/wshobson/agents/blob/main/docs/agents.md)).

Synthesis is small, mechanical and a script: `synthesize.mjs` parses the three lens files into findings, merges duplicates, applies the rules and writes `findings.json`, the only thing the merge rule reads (prose in `review.md` is for humans). Two duplicates merge only when they are in the same file within five lines **and** their claims overlap (Jaccard over content words ≥ 0.15) or they carry the same CWE; "same lines" alone merged a P1 body-limit finding with an unrelated P2 ask on the neighbouring line during the dry run and the "ask wins" rule then demoted the P1. Severity is the maximum across lenses; `action` missing is `ask`; any member `ask` makes the group an ask. Two rules were added by the dry run: a finding that cites a spec anti-goal is at least P1 (which moved qa's F-001 into the fix loop), and on `persuade` or `operate` surfaces a UI lens `disposition: fix` is itself an open P1 until a UI re-review says `ship`. Each finding carries `status: open | resolved | pr | deferred`, with resolutions supplied as data (`resolutions.json`, written by the re-reviewer) rather than inferred from prose. Disposition: any open P0 or any open `ask` → `ask` (one attention item listing them with a recommendation and two or three options, Archon's and marshal's format); open P1 with `action: fix` → `fix`; otherwise `ship`. Only P0/P1 items enter the fix loop, as wshobson's `full-review` does by forwarding a "Critical Issues" subsection rather than whole reports ([full-review](https://github.com/wshobson/agents/blob/main/plugins/comprehensive-review/commands/full-review.md)). The review fix loop is capped at **two rounds**: each round resumes the implementer with the open P0/P1 list, re-runs `verify.mjs --full`, and re-runs only the lenses that had findings against `FIX_BASE..HEAD`; on round-2 failure the run goes to `needs-human` with the open findings ([final-review](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/references/final-review.md)). P2 `fix` items land in the PR as findings; P3 go to `deferred.md` and never loop, following bmad's `defer` route and Superpowers' "Minors never enter the loop".

### Review stage, expanded: a touch mask, real application security, and the rest of the audit

The three lenses above cover spec compliance, code quality, UI fidelity and dependency hygiene. As first written, the "security auditor" was secrets-and-dependency hygiene plus one authorization trace; that is not application security for a multi-tenant product, and the review also left out a set of cheap deterministic checks that catch what agents characteristically leave behind. This section adds both without adding agents: one classifier script decides which checks a given diff earns, the deterministic checks run as scripts, and the single new agent pass runs only when the diff touches a trust boundary.

**The touch mask.** `classify-diff.mjs` reads `review.diff` and the changed-file list and writes `touches.json`: a set of booleans, each with the file paths or patterns that triggered it. The categories are `auth`, `data`, `network`, `files`, `crypto`, `config`, `deps`, `native`, `api_contract`, `ui`, `tests` and `analytics`. The shipped defaults are deliberately conservative: paths match as directory or file segments (`/auth/`, `/guards/`, `/migrations/`, `schema.prisma`), and content patterns are specific (`@UseGuards`, `jsonwebtoken`, `bcrypt`, `prisma.`, `\bfetch(`, `randomBytes`), because the dry run's first draft matched the substrings "signup", "token" and "client" and fired `auth` and `files` on a diff with no auth code and no file handling; the tightened rules fire `data`, `network`, `crypto` and `api_contract` on the same diff, which is what it contains. Setup section C adds the project's real auth and data directories so a helper three files away from a controller still trips `data`. The mask is what keeps the expanded review affordable: a copy change gets scanners and hygiene and nothing else, a new endpoint gets everything below. Its tradeoff is that a classifier under-reports, so the code reviewer is told that an endpoint added without `auth` or `data` firing is itself a `P1 ask`.

**Layer 1: deterministic security, every run.** `security-scan.sh` is organised as capabilities, each satisfied by whichever tool is available, and a capability with no passing tool is `missing`, never a pass. Secrets: `gitleaks` on the branch's commits, or `secretlint` from npm when gitleaks is not installed ([gitleaks](https://github.com/gitleaks/gitleaks); [secretlint](https://github.com/secretlint/secretlint)). Vulnerabilities: `pnpm audit --audit-level=high --prod` (or `npm audit`), with `osv-scanner` as an optional second source that never blocks ([OSV](https://google.github.io/osv-scanner/usage/scan-source/)). SAST: semgrep with a committed `.factory/semgrep/` directory of project rules that always runs, and the registry packs (`p/typescript`, `p/nodejs`, `p/react`, `p/owasp-top-ten`) when the registry is reachable, recorded as `partial` when it is not (it was not reachable from the dry run's environment) ([Semgrep registry](https://semgrep.dev/explore); [Semgrep CLI](https://docs.semgrep.dev/cli-reference)). The project rules are the ones that catch what agents actually write: `dangerouslySetInnerHTML`, `eval`/`new Function`, shell commands and SQL built from template literals, server-side fetch of a request-supplied URL, an analytics `track()` call carrying `email`/`ip`/`name`, and a `VITE_`/`NEXT_PUBLIC_` variable named like a secret. Setup proves them the way it proves every check: zero findings on the current tree and three on a planted-bug file. The PII rule excludes test files, because the tests that prove the allowlist strips `email` call `track()` with an email on purpose; that was the first false positive the dry run produced. Everything is baselined to the merge base so only findings introduced by the branch count, a committed `.factory/security-accepted.json` holds fingerprints a human has waved through, and the security reviewer has `memory: project` so the same false positive is not re-argued on every run. The lint step gains `eslint-plugin-security` and `eslint-plugin-no-unsanitized`; two small checks no scanner does also run: a `NEXT_PUBLIC_`/`VITE_` audit listing every new client-exposed variable, and a new-dependency report (install scripts, maintainer count, licence) so the reviewer sees supply-chain risk rather than a bare name; `trivy` and `hadolint` run only when a Dockerfile changed. The merge fact `security_scanners_ran` passes only when every required capability (secrets, vulnerabilities, project-rule SAST) has a `pass` or `partial` tool.

**Layer 2: the trust-boundary trace, when `auth`, `data`, `network`, `files` or `crypto` fire.** The security reviewer is not asked to "consider OWASP"; it is given a mechanical procedure that language models execute reliably. For every new or changed entry point in the diff (endpoint, server action, webhook, job, or screen that calls one), it writes one row: entry → authentication check → authorization check → input validation → data access and whether every query is scoped to the caller's user or organisation → what leaves in the response. Any empty cell is a finding with a CWE id, and the trace table itself is attached to `review-security.md` so the human can audit the audit. The checklist behind the trace, in the order that matters for a Next.js, NestJS and Expo stack: authorization and tenant isolation (every query that takes an id must be scoped; this is the most common defect in generated multi-tenant code); input handling (`ValidationPipe({ whitelist: true, forbidNonWhitelisted: true })` on Nest, a zod parse on every Next.js action and handler, mass assignment on update endpoints); injection and SSRF (raw SQL, shell, path traversal, any server-side fetch of a user-supplied URL); CSRF on cookie-authenticated route handlers, which unlike Server Actions get no origin check from Next.js ([Server Actions security](https://nextjs.org/docs/app/guides/data-security)); rate limiting on anything public (login, signup, password reset, webhooks) and signature verification on inbound webhooks; secrets and logs (tokens or PII logged, stack traces returned, missing exception filters); mobile (tokens in `expo-secure-store` rather than AsyncStorage, deep-link parameter validation, no secrets in the bundle) ([SecureStore](https://docs.expo.dev/versions/latest/sdk/securestore/)); migrations (destructive operations, new foreign keys without indexes). Severity is fixed, not judged: authorization bypass, tenant leak, secret exposure and injection are always `P0 fix`, and `merge-decision.mjs` treats any open P0 from this lens as a hard `needs-human` regardless of every other fact.

**Layer 3: runtime checks, PR time only.** Two are worth the cost. First, a rule rather than a tool: a new protected endpoint without a negative authorization test (call it as the wrong user or tenant, expect 403 or 404) is a `P1 ask`; the factory asks the implementer for that test in the plan when `auth` fires, so most runs arrive with it. Second, an OWASP ZAP baseline scan against the running dev server for headers, cookie flags and obvious misconfiguration ([ZAP baseline](https://www.zaproxy.org/docs/docker/baseline-scan/)). ZAP has the same constraint as Playwright (the app must be reachable outside Claude's Bash sandbox) and is noisy, so it runs from the PR workflow, not in the loop. Anthropic's own `/security-review` command and the `anthropics/claude-code-security-review` GitHub Action are a third option: an independent diff review with built-in false-positive filtering that costs no plugin work ([announcement](https://www.anthropic.com/news/automate-security-reviews-with-claude-code); [action](https://github.com/anthropics/claude-code-security-review)). Benefit: a second opinion you did not write. Tradeoff: it knows nothing about your tenant model, so it cannot replace the trace, and it spends a full review's tokens per PR; run it on PR open, outside the loop.

**The rest of the audit.** Everything below is a script unless marked otherwise, and each is gated by the touch mask.

**Further checks, by what the feature is.** A second set of checks completes the audit. Six are deterministic scripts that run in v1 whenever their touch fires, and they cover the places where the checks above look only at what the plan named or only at source rather than output. Visual regression on *unchanged* routes: a CSS change for one screen breaks another, and nothing above looks at routes the plan did not name, so `capture-web.sh` also captures the app's top routes from the recipe and compares them with the captures stored at the last merge using Playwright's `toHaveScreenshot` threshold; a diff above it is a `P1` ([toHaveScreenshot](https://playwright.dev/docs/test-snapshots)). A built-bundle secret scan: the `NEXT_PUBLIC_` audit covers environment variables, not a key hardcoded in a file that ends up in the client, so gitleaks also runs over `.next/` and the Expo export output, and the same step fails if source maps are in the production output. Migrations run both ways: safety was only read above, so when `data` fires `verify.mjs --full` runs `up → down → up` against the dev database and data loss on the way down is a `P1`. Mobile permissions and store compliance: a new permission API without an `Info.plist` usage string, or a new SDK (analytics included) without a matching entry in `PrivacyInfo.xcprivacy` and the Android data-safety notes, is an App Store or Play rejection weeks later, so a script compares new permission and SDK usage with the declared strings and manifests when `native` or `deps` fires ([privacy manifest](https://developer.apple.com/documentation/bundleresources/privacy-manifest-files)). Localisation completeness: when setup recorded i18n, `i18next-parser` or `lingui extract --check` fails on a new string with no key. Time handling: when `data` fires, the code reviewer's checklist includes timezone, DST and date-boundary handling, and a rule that tests touching dates freeze the clock, because EU multi-country products hit these constantly.

The rest are gated by what the feature is, and two of them ship in v1 because the `qa` walk as described is UI-centric and a factory for a product with a backend cannot be. First, a criterion type `trigger-and-observe` for backend-only behaviour (a nightly job, a queue consumer, a webhook): the plan writes the criterion as "enqueue or replay this recorded payload, then assert this side effect (a row, an email in the sink, an outbound call recorded by the mock)", and `qa` executes it through `curl` and the recipe's commands rather than through a screen. Second, the mobile upgrade path: when `native` fires or a persisted-storage schema (AsyncStorage keys, SQLite tables) changes, `capture-mobile.sh` installs the previous build from the last merge, seeds state by walking one flow, applies the update, and relaunches; a crash on old persisted state is a `P0`. The remainder are v2, each a touch-gated addition rather than a new stage: emails, push and SMS verified through a dev sink (Mailpit for email, Expo's push tool in development) with `qa` asserting the message exists, renders and its links resolve; feature flags for `l` features verified in both states with the production default confirmed off; inbound integrations verified by replaying recorded webhook payloads, including one with a bad signature, as fixtures; offline and poor-network behaviour on mobile through simulator network conditioning for features that queue or sync; a 30-second `autocannon` or k6 smoke against changed endpoints with 10k seeded rows when `api_contract` and `data` both fire, which is the cheapest thing that catches an N+1 unit tests cannot; a PR-time Playwright project on WebKit for web and captures on both iOS and Android rather than one for mobile; rolling-deploy safety as a reviewer checklist item when `data` fires (expand/contract: new code against the old schema and old code against the new, since both run during a deploy); and the Lighthouse SEO category on changed public routes.

Three things the factory deliberately does not verify. Whether the feature is the right feature: the spec gate and the "how will you know this worked" question are the only tools, and they face the human on purpose. Production behaviour after merge, which belongs to CI and monitoring with the factory only watching (next section after the merge rule). Race conditions and concurrency bugs, which are a reviewer checklist item and not a gate, because nothing cheap catches them reliably.

**Blocking versus reported.** Every row added here is a way for the fix loop to burn rounds on something other than correctness, so the blocking set stays small: red gates in `evidence.json`, P0 from any lens, an `ask` from any lens, and a breaking `contract.json` when the project has a mobile app. Everything else lands in the PR as P1/P2 findings with locations, and in `deferred.md` if P3. The hygiene and contract scripts add seconds; axe adds a few seconds per route; the trust-boundary trace is the only expensive addition and it runs on perhaps a third of diffs. The deliberate omission is a fourth agent for performance or resilience: those checklists are folded into the code reviewer's prompt as sections that activate on the mask, because Superpowers' and wshobson's experience is that more reviewers mean more tokens and more gaming without better findings.

### PR and the merge-confidence rule

The PR body is rendered by scripts, not written by an agent. `pr-inputs.mjs` extracts everything the PR needs into `pr-inputs.json` (title, summary from the spec's Goal, commits and diff stat, the evidence table from `evidence.json`, per-criterion status from `qa.json`, analytics verdicts, resolved and open findings from `findings.json`, the security capabilities, the implementer's `assumptions` and `assessment` blocks verbatim, up to six screenshots, the preview URLs, and the local start commands), and `pr-render.mjs` renders `pr.md` from it for zero tokens: a title prefixed with the ticket key, a `Needs a decision` section for open asks, an evidence table (check, result, duration, SHA), and a `Verify in 2 minutes` section with one numbered step per success criterion against the preview URL or the local commands. The dry run tried the agent route twice: a haiku writer that read the artifacts cost 192k tokens, and one fed the pre-built JSON still cost 120k, because each tool call carries the system prompt and tool schemas; a template costs nothing and its only loss is slightly flatter wording of the verify steps, which the spec template already requires to be written as route, action and expected observable. An agent is dispatched for this stage only when prose polish is explicitly wanted. The orchestrator then runs `gh pr create --draft` (or ready, per config) and optionally `gh pr checks --watch` once; a red CI run from a provider-attributed flake is re-run once (Archon's rule), a red from the change gets one CI fix round in v2, and anything else is `needs-human` ([CONSTITUTION](https://github.com/coleam00/archon/blob/dev/.archon/workflows/sdlc/CONSTITUTION.md)).

The merge decision follows marshal-factory's principle that hard limits "are facts, not the agent's judgement", so `merge-decision.mjs` computes it and the agent contributes one typed input ([operations](https://github.com/ski043/marshal-factory/blob/main/docs/operations.md)). The script returns `merge` only when every fact holds: `evidence.json.sha` equals the PR head and `dirty=false` and `trusted=true`; all recipe checks passed; GitHub checks are green at that head; no merge conflict; `findings.json` has disposition `ship` with zero open P0/P1 and zero open `ask` (read from the status fields, never from prose); every required security capability passed; `security.json` has no high/critical items; UI files changed implies captures attached; the diff touches none of `.github/workflows/**`, lint/CI configs or `.factory/setup.json` (always handover, with one sanctioned exception: a scaffold run, `state.scaffold === true`, may create the recipe); factory scripts are not part of the product diff because they live in the plugin; blast radius is under the configured thresholds (files changed, no migrations unless the ticket is typed `maintenance` and approved); the triage size is not `l`; the implementer's assessment is `{recommendation: "merge", confidence: {confident: true, reason}}` and the schema refuses a merge without confidence or a reason, as marshal's does; and the run spent fewer dispatches than the cap. Any false fact yields `needs-human` with the failing facts listed. `config.merge` then decides what happens: `off` posts the decision as a PR comment, `trial` posts "Would merge (trial)" (marshal's mode for building trust), and `auto` merges with `--sha` pinned to the evaluated head so a push in between makes GitHub refuse, then watches main for 60 minutes and opens a revert PR on red. v1 ships with `trial` as the recommended default; the notes record HumanLayer shutting down its lights-off factory after about four months and marshal's own author listing oracle gaming and evaluator leniency as the known failure modes, so earn `auto` on your own data ([factory-concepts](https://github.com/ski043/marshal-factory/blob/main/docs/research/factory-concepts.md)). One more fact joins the list once previews exist: if a `github-deployment` preview is configured for an app the diff touched, that deployment must have reached `success` for the PR head; a failed or missing preview build is `needs-human`.

### After merge: watch, never deploy

The pipeline as described ends at merge, and in `auto` mode that is its most dangerous moment: code has just landed on `develop` or `main` with nobody looking. The post-merge step is deliberately small, because deployment and monitoring belong to CI and the host, and the factory's job is to observe them and to open a revert when the facts say so.

`post-merge.mjs` runs as a background task after a merge, in `auto` mode automatically and in `trial` and `off` modes on your manual merge of any PR carrying the `factory` label, so the data exists before `auto` is ever switched on. It watches the target branch's CI for the merged SHA with `gh run watch`; when the host's deployment for that branch reaches `success` (staging for `develop`, production for `main`, read from the same GitHub Deployments API as previews), it runs the smoke set against the deployed URL: the Playwright specs and Maestro flows this run pinned, plus its `trigger-and-observe` criteria where they are safe to run against a live environment (the plan marks each one). The result is one line in `log.md`: `post-merge: <run> ci=green deploy=success smoke=pass`. Nothing here deploys anything. The factory never runs `vercel deploy`, `eas submit` or a migration against production; if the host deploys on merge the factory observes, and if it does not, the merge is the end of the factory's job and a human deploys.

The revert path is the only action. If CI is red at the merged SHA, or the smoke set fails inside the watch window (60 minutes), the factory opens a revert PR against the target branch with the failing evidence attached and labels it `needs-human`; it never merges the revert itself. For a hotfix that has already been back-merged, the revert targets both `main` and `develop`. The watch window ties up a background session for up to an hour, which is acceptable for one feature at a time, and a flaky production smoke will produce revert PRs that have to be closed by hand, which is the cost of having the net at all.

An error-rate watch is v2 and off by default. When setup section L records an error tracker (detected from its SDK, with a read-only API key), `post-merge.sh` compares the release's new-issue count and error rate during the window with the hour before, and a spike above a configured threshold takes the same revert-PR path. It catches the one failure class that passes every test, a runtime error on real data; the tradeoffs are another credential, noise on low-traffic apps, and the need for a baseline that a new product does not have. The retro closes the loop: a post-merge failure is the most valuable input `/factory-retro` receives, because it is a case where every gate passed and the change still broke, which is exactly when a new lesson, golden task or gate is justified, so the retro reads `post-merge:` lines first. Feature flags and canary rollouts are v3 at most, and only if the data shows a need.

### Previews and the two-minute verification

Nothing above gives the human a cheap way to try the feature, and that is the oracle that catches "it does what the spec says but not what I meant". The fix is deliberately not a set of hosting adapters. The factory assumes nothing about where the product runs; it assumes only that if a host builds branches, it reports a deployment to GitHub, and if nothing does, the developer can run the branch locally.

`preview.mjs` runs once the PR is open and writes `runs/<id>/preview.json` with one entry per app. For `github-deployment` apps it polls `gh api repos/{owner}/{repo}/deployments?sha=<head>` and the deployment's statuses until one reports `success` with an `environment_url`, or the wait budget expires; Vercel, Netlify, Cloudflare Pages, Railway and Render all post these without any factory-side configuration ([GitHub Deployments API](https://docs.github.com/en/rest/deployments/deployments); [deployment statuses](https://docs.github.com/en/rest/deployments/statuses)). For `command` apps it runs the configured command with `{branch}`, `{title}` and `{sha}` substituted and reads the URL from the output with the configured JSON path; the EAS example (`eas update --branch factory/<slug> --json`) produces an update a dev-client build can open from a link or QR code ([EAS Update](https://docs.expo.dev/eas-update/getting-started/)). For `fixed` apps it records the shared staging URL. Each entry carries `status: ready | failed | timeout | none` so the PR body states what it could and could not provide.

The PR body always ends with a **Verify in 2 minutes** section, for every ticket size. The haiku `pr-writer` derives it from the spec's `SC-###` success criteria (or, on the `oneshot` route, from triage's `acceptance_check`): numbered steps of the form "open `<preview>/dashboard`, click Export, expect a CSV with the three columns from SC-2", one step per criterion, with the mobile steps pointing at the update link and the screen name. When no preview exists for an app, the section says so and gives the local equivalent from the recipe instead: `git fetch && git checkout factory/<slug> && pnpm --filter web dev`, then the same steps against `http://localhost:3000`. A `/factory try <run>` skill does that checkout and start for you and opens the first route the plan names, so the local path is one command rather than four.

Two refinements are v2. The first is database previews: for tickets where the touch mask fired `data`, a database branch per PR (Neon's GitHub integration creates one automatically; Supabase branching does the same) so the preview runs real migrations against real-shaped data, which is why marshal-factory standardised on Neon ([Neon branching](https://neon.tech/docs/introduction/branching)). Without it, previews point at shared staging and a migration is only proven by the integration tests. The second is closing the loop: when you try the feature and comment on the PR, `/factory resume <run>` reads unresolved PR review comments and treats them as one `ask` round, so your words reach the implementer as findings with locations rather than as a fresh prompt.

Benefits: the human check costs two minutes instead of a checkout, the PR-time capture and accessibility pass can target the preview URL instead of `localhost` (which removes the sandbox constraint for that stage), and the factory carries no host-specific code. Tradeoffs: preview environment variables have to be configured once on the host, outside the factory; hosts that post no deployment need a custom command; a preview is JS-only for mobile (the `ota.json` detector already flags native changes that cannot ship this way); and a preview backend per PR costs money and cold starts, which is why the default is a shared staging API unless the ticket touches `data`.

### Fallbacks when Linear or Notion are absent

The in-repo layout is the source of truth regardless of integrations; trackers and docs are mirrors. Without Linear, tickets are `.factory/tickets/<feature>/NN-slug.md` with mattpocock's `Status:` line (`ready-for-agent | in-progress | in-review | built | done | blocked | dropped`, bmad's vocabulary mapped to his file shape) and `## Comments` appended at the bottom ([issue-tracker-local](https://github.com/mattpocock/skills/blob/main/skills/engineering/setup-matt-pocock-skills/issue-tracker-local.md)). With Linear, the orchestrator creates one issue per ticket after the ticket gate (parent issue = feature, labels carry `type`, relations carry blocking), writes the issue URL into the ticket frontmatter, and maps status transitions `in-progress → In Progress`, `in-review → In Review`, `done → Done`, `dropped → Canceled` as bmad's starter does; it never reads the tracker mid-run, because bmad labels its tracker stores "lightly tested" and because every MCP read costs schema tokens ([linear-ticketing.toml](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmad-agent-po/config/linear-ticketing.toml); [ticketing-and-epics](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmod-method/help/ticketing-and-epics.md)). Without Notion, `spec.md` lives at `.factory/specs/<feature>/spec.md` and the PR links to it; with Notion, the orchestrator pushes the approved spec as a page once, stores the URL in the spec frontmatter, and all later stages still read the repo copy. The same rule applies to the Figma screenshot and Mobbin references: fetched once at spec or plan time, cached under `runs/<id>/references/`, never re-fetched by reviewers (Figma's 10–15 reads per minute would throttle parallel subagents; Mobbin URLs expire in 30 days) ([Figma rate limits](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/); [Mobbin features](https://docs.mobbin.com/mcp/features)).

### Per-project memory

`.factory/` follows the Karpathy gist's three layers: raw sources are the immutable run artifacts (`runs/<id>/{triage,research,grill,spec,plan,implementation,review,evidence,decision}`), the wiki is `knowledge/*.md` (module notes, decisions as ADRs, gotchas) plus `lessons.md`, and the schema is `.claude/rules/factory.md`; `index.md` catalogues what exists and `log.md` is append-only with fixed prefixes (`run:`, `lesson:`, `decision:`, `escalation:`) that scripts can grep ([gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). The triager and planner read `index.md` first, then only the knowledge pages it names, nvk/llm-wiki's "indexes first, never scans blindly" rule ([nvk/llm-wiki](https://github.com/nvk/llm-wiki)). Three Claude Code mechanisms are used as-is instead of reimplemented: `CLAUDE.md` for the six-line managed block (bmad's policy that stack lists and directory trees stay out because "Every line loads in every session, and agents follow instructions less well as the loaded set grows"), `.claude/rules/factory.md` for the always-on invariants, and `memory: project` on the two reviewer agents so repo-specific calibration persists in `.claude/agent-memory/<name>/` and is committed ([project-context](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmod-method/help/project-context.md); [memory docs](https://code.claude.com/docs/en/memory); [sub-agents](https://code.claude.com/docs/en/sub-agents)). Claude's own auto memory is left alone; the notes say it is machine-local and not loaded into subagents, so it is the wrong place for team-shared facts.

Lessons are human-gated. `/factory-retro` runs after a merged run (or every tenth, mattpocock's throttle) and reads the run's artifacts, `log.md` and the diff; it proposes at most three items, each classified the way his `retro` skill does: a mechanical rule becomes a proposed hook or lint rule, a judgement call becomes a line in `lessons.md`, a navigation fact becomes a line in `index.md`, and a hard-to-reverse decision becomes an ADR under `knowledge/` ([retro](https://github.com/mattpocock/skills/blob/main/skills/engineering/retro/SKILL.md)). The user approves each; nothing is written live, which is one-skill-to-rule-them-all's staged-update discipline without its always-on cost ([task-observer](https://github.com/rebelytics/one-skill-to-rule-them-all/blob/main/SKILL.md)). `lessons.md` is capped at roughly 60 lines and the planner is the only agent that reads it in full; the implementer gets only the lines the plan quotes.

### Token-efficiency rules

Every rule here traces to a measured or documented failure. Skills stay under the spec's 5,000-token body and 500-line limit, with loop rules in `run-state.mjs` rather than prose, because of the compaction truncation above; the plugin's CI runs Superpowers' size test (`fail any SKILL.md ≥ 20,000 bytes`) ([spec](https://agentskills.io/specification); [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). Only `/factory` and `/setup-factory` are model-invocable; everything else is `disable-model-invocation: true` or `user-invocable: false`, keeping the always-on listing cost to two descriptions ([skills docs](https://code.claude.com/docs/en/skills)). Artifacts are passed by path, dispatch prompts are five lines (where this fits, the brief path, interfaces the brief cannot know, the ruling on any ambiguity, the report path), subagents return under 15 lines and write the rest to a file, and each artifact is capped near 300 lines ([SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). Models are declared on every dispatch ("An omitted model inherits your session's model"; one Superpowers run "put all 26 of its reviewers on the top tier") using Archon's and wshobson's tiers: sonnet for triage, research, implementation, UI review and security; opus for spec, plan and code review; haiku for the PR body; scripts for verify, scan and merge ([tier-defaults](https://github.com/coleam00/archon/blob/dev/packages/workflows/src/defaults/tier-defaults.json); [ARCHITECTURE](https://github.com/wshobson/agents/blob/main/ARCHITECTURE.md)). The hook-injected codebase map is ponytail's script unchanged: `git ls-files` plus a regex per language, 2,000 characters, folders of shared code first, a 3-second fail-open budget, injected at `SessionStart` and `SubagentStart` so implementers and reviewers see it without reading files ([ponytail-map.js](https://github.com/dietrichgebert/ponytail/blob/main/hooks/ponytail-map.js)). Parallelism is reserved for read-only stages (two researchers, three reviewers); implementers run one at a time per branch, which both wshobson and Superpowers enforce ("Never dispatch multiple implementation subagents in parallel") ([SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md)). No subagent is used where Anthropic's guidance says not to: grilling (back-and-forth), the `oneshot` route for `s`-size work (a quick targeted change), and synthesis steps that only concatenate files ([sub-agents](https://code.claude.com/docs/en/sub-agents)). Verification, scanning, capture and the merge decision are scripts, which cost zero tokens and cannot be talked out of a result; fix rounds never run the full suite; browser work uses `playwright-cli` rather than an MCP whose ~18k-character schema would sit in every turn; and MCP servers for Linear, Notion, Figma and Mobbin are called by the orchestrator in short bounded steps rather than being available to every subagent, keeping ECC's "fewer than 10 MCPs, fewer than 80 tools" budget intact ([README](https://github.com/affaan-m/ecc/blob/main/README.md)). The earlier report's note on Anthropic's October 2026 guidance about folding subagents back into a single context applies here in one place: if a run's size is `s`, the whole thing should be one context, and the orchestrator should say so rather than dispatching five agents to change a label.

## Every optional integration costs something; most belong in v2 or v3

Each integration is a setup-time choice with a working fallback, and the table states what it buys and what it costs, so the decision can be revisited per project rather than baked in.

| Integration | Benefits | Tradeoffs | Placement |
|---|---|---|---|
| **Linear (MCP, `https://mcp.linear.app/mcp`)** | A real board, blocking relations and history the user already uses; marshal shows how clean the write-back can be (In Progress on claim, In Review with PR link, Done on merge, `factory-failed` label to stop loops) ([operations](https://github.com/ski043/marshal-factory/blob/main/docs/operations.md)). | Every MCP read costs schema tokens; bmad calls its tracker stores "lightly tested"; two sources of truth drift unless the repo stays canonical; the factory must own label and state names as typed config ([ticketing-and-epics](https://github.com/bmad-code-org/bmad-method/blob/main/skills/bmod-method/help/ticketing-and-epics.md)). | v2 as a write-only mirror; v1 local tickets. |
| **Notion (docs)** | Specs readable and commentable by non-engineers; one page per feature with a stable URL in the PR. | Same drift and token cost; agents reading Notion mid-run is slow and large; a Notion page is not diffable or reviewable in a PR. | v2, push-once after spec approval; v1 `.factory/specs/`. |
| **Mobbin (MCP, Pro/Team plan)** | 600,000+ real screens via `search_screens`/`search_flows` with no browser automation; good for onboarding/empty-state patterns the spec names ([mobbin.com/mcp](https://mobbin.com/mcp)). | $10–15/month, "unlimited during beta" with limits promised later, image URLs expire in 30 days so picks must be downloaded, and the screens are other companies' copyrighted UI, usable as references only ([pricing](https://mobbin.com/pricing.md)). | v2 optional spec step; fallback is a `references/` folder of your own screenshots. |

| **TestSprite** | An independent, PRD-driven E2E plan reduces "the agent tests its own assumptions"; hosted browsers, screenshots, a fix loop ([workflow](https://docs.testsprite.com/mcp/workflow)). | Minutes per cycle plus cloud cold starts, credits never defined, Python+Playwright output that does not run under a TS toolchain, no documented way it reaches `localhost` (a liability inside any sandbox), no mobile coverage found, and only affiliate-grade third-party evidence ([pricing](https://www.testsprite.com/pricing); [hands-on](https://dev.to/asta_jui_6/review-developer-mencoba-testsprite-mcp-di-proyek-nyata-pengalaman-dari-developer-indonesia-1bjf)). | v3 at most, nightly or review-time, web only; Playwright's planner/generator/healer agents cover the same need in TypeScript ([test agents](https://playwright.dev/docs/test-agents)). |

Two design-level recommendations deserve the same treatment. Running stages as built-in subagents (rather than `claude -p` processes) is cheaper to build, needs no daemon, keeps subscription auth, and gets fresh context by construction; the cost is that the orchestrator's context still grows with every dispatch and return (hence the 15-line return rule), subagents inherit the session's working directory (so worktree-per-run means rooting the whole session in the worktree, declaring `isolation: worktree` on the implementer agent, which the sub-agents docs describe as "branched from your default branch", or falling back to `claude -p` in v2), and the notes record no repo that has proven `isolation: worktree` across a multi-stage pipeline, so treat it as the first thing to test in v2 rather than a v1 assumption ([sub-agents](https://code.claude.com/docs/en/sub-agents)). Making verification and merge decisions scripts rather than agents removes token cost and oracle gaming, but it means the recipe must be right (hence proving it at setup) and that a project with no test command gets a weaker gate, which the judge then reports as a fact ("no test check in recipe") rather than hiding.

## Keep v1 small: web-only, one implementer, trial merge, manual retro

The strongest evidence in the notes is about what not to build. Superpowers removed per-artifact review loops because five versions times five trials showed "identical quality scores" with or without them, cut two reviewers per task to one, and deleted "pause every 3 tasks"; marshal's author lists oracle gaming, evaluator leniency and context failures as the ways factories die; bmad's maintainers write "Prefer deleting an instruction to hedging it"; and Archon's constitution adds determinism "only after a real run failed in a way an agent node can't handle" ([release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md); [factory-concepts](https://github.com/ski043/marshal-factory/blob/main/docs/research/factory-concepts.md); [AGENTS.md](https://github.com/bmad-code-org/bmad-method/blob/main/AGENTS.md); [CONSTITUTION](https://github.com/coleam00/archon/blob/dev/.archon/workflows/sdlc/CONSTITUTION.md)).

Leave out of v1: parallel implementers and worktrees (claude-squad and mattpocock show how, but the user runs one feature at a time and the orchestration cost is the daemon everyone else built); Modal, TestSprite, Mobbin, Figma and Notion (each needs accounts, keys or seats and none changes whether the pipeline works); automatic learning (ECC's instincts and base's correction detector have no published evidence of useful output; a human-gated retro does the job); auto-merge (ship in `trial`); Maestro-pinned mobile flows (v1 runs every configured app, including the mobile app on a simulator through `mobile-mcp`, and walks the criteria; it pins web flows as Playwright specs but leaves Maestro YAML generation, which needs Java, to v2); PR-time CI fix rounds (let GitHub CI be the final validation; v1 only watches it, before merge for the merge fact and after merge in `post-merge.sh`); separate UX and UI reviewers (one UI reviewer with two sub-passes); Agent Teams (experimental flag); and any Stop-time hook beyond the config guard (impeccable's two-tier hook design is elegant but its engine is a 20 MB download with telemetry).

Build order. **v1** (the first two weeks of evenings): plugin skeleton and marketplace; `setup-factory` with detection, the eight sections, recipe proving and marker-managed writes; `/factory` with triage, research, grilling, spec with builder check and hard gate, tickets, per-ticket plan, implementer, `verify.mjs`, `run-apps.sh` and the `qa` agent walking every criterion on every configured app (web via `playwright-cli`, mobile via `mobile-mcp`, vision as the bounded fallback) with web flows pinned as Playwright specs, `sync-base.sh` with escalate-on-conflict, the three review lenses, PR body with the "Verify in 2 minutes" section, `preview.sh` reading GitHub Deployments with the local fallback and `/factory try`, `merge-decision.mjs` in trial mode, local tickets and repo specs, `.factory/` memory with manual `/factory-retro`; git-flow lanes chosen by triage with the hotfix back-merge; `.factory/env.local` as the only run environment; analytics in the spec and verified in the walk; the six deterministic extra checks, `trigger-and-observe` criteria and the mobile upgrade path; `post-merge.sh` with the revert PR; ten evals (one per stage prompt) under `evals/` and the six golden tasks with their first scorecard. Measure a dozen real runs: tokens per stage, rounds used, P0/P1 counts, time to PR, how often `needs-human` fires and why. **v2** (tested on the dry-run repo except where the section above says otherwise): database branches per PR for `data` tickets and PR comments as an `ask` round; the error-rate watch after merge; the touch-gated extras (email/push sinks, feature-flag states, webhook replay, offline conditioning, endpoint load smoke, WebKit and dual-platform captures, SEO); Linear write-back and Notion push; Figma fetch at plan time; Maestro mobile capture and the Expo craft skill; CI watch with one flake re-run and one fix round; `claude -p` worktree runs via `scripts/run-stage.sh` for two tickets in parallel; `npx impeccable detect --json` as an optional deterministic UI pass; the plugin exposed through `npx skills add` for non-Claude agents. **v3**: Modal for third-party repos and parallel E2E; TestSprite as a nightly second opinion; `auto` merge with revert-on-red once trial decisions have matched your own judgement for a month; headroom and herdr as user-level options, measured.

## The two diagrams get the shape right and the mechanics wrong

The theSeniorDev diagram (spec-writer → builder → parallel security/UX/UI/code reviewers → wait for all → approver → merge or needs-human, max 2 rounds) matches the research on three points: parallel fan-out is right only for read-only reviewers, a single approver that can say `needs-human` is the correct escalation primitive, and two rounds is where Superpowers' and wshobson's measured or chosen caps landed. It is wrong, or silent, on the parts that the evidence says decide outcomes. There is no triage, so a bug and a feature take the same path and nothing decides whether the request is specifiable; there is no human gate on the spec, which Superpowers measured as the difference between 24/24 and 3/24 runs skipping the design; "wait for all" implies pasted reviewer output, when every working system hands over files; the approver is drawn as an agent, whereas marshal's lesson is that merge facts must be computed and the agent's only contribution is a typed confidence with a reason; and splitting UX from UI reviewers duplicates the expensive part, since impeccable's isolation is between deterministic evidence and visual judgment, not between two kinds of taste ([playbook](https://github.com/ski043/marshal-factory/blob/main/playbooks/factory.md); [impeccable critique](https://github.com/pbakaus/impeccable/blob/main/.claude/skills/impeccable/reference/critique.md)). Nothing in it addresses verification as a tamper-evident script, test-integrity hooks, or state and resume.

The ZazenCodes diagram (ingest → triage → refinement → prioritizer → implementor ×N with worktree and sandbox each → build and quality pipeline → PRs → AI reviewer → blast radius → staging → QA agent → production; fail → fix → 3 retries → escalate) is the marshal-factory and Archon shape, and its best ideas survive into this design: typed triage, a prioritiser that produces slices, a blast-radius check in the merge rule, and three retries before escalation. Its problems are cost and operational surface rather than logic. N parallel implementors each in a worktree and a sandbox is precisely the part that forced marshal into a Bun daemon, Postgres, launchd and three cloud services, and Archon into a server with its own database; neither is a Claude Code plugin, and the notes record no plugin that spawns worktree runs itself ([README](https://github.com/ski043/marshal-factory/blob/main/README.md); [Archon README](https://github.com/coleam00/archon/blob/dev/README.md)). A sandbox per implementor on Modal is ≈$0.38 per sandbox-hour on top of tokens, and inside Claude Code's own sandbox the QA step the diagram relies on cannot reach `localhost` or start Chromium ([sandboxing](https://code.claude.com/docs/en/sandboxing)). "Staging → QA agent → production" is deployment automation that belongs to CI, not to a plugin, and the diagram omits the spec gate, the evidence rules that stop an agent from rewriting `package.json` scripts to `true`, and any memory. Both diagrams share a blind spot: they draw boxes and arrows but say nothing about what travels along the arrows, and the research is unambiguous that pasted context (a 42,000-character dispatch, 18 fix rounds after a truncated skill, cross-plan ledger contamination) is where real pipelines failed ([SDD](https://github.com/obra/superpowers/blob/main/skills/subagent-driven-development/SKILL.md); [release notes](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)). Treat the diagrams as a target topology for v3 and the file-and-script mechanics above as the thing to build first.

## Conclusion

The useful discovery is that the factory problem has already been decomposed into contracts by people running real pipelines, and the contracts are portable even though the runtimes are not: Archon's triage JSON, bmad's plan status machine, marshal's evidence and merge facts, no-mistakes' finding model, Superpowers' brief/report/diff files and round caps, mattpocock's grilling and ticket layout, impeccable's reviewer disposition. A Claude Code plugin can carry all of them as Markdown and ~2,000 lines of dependency-free Node, with the one architectural commitment that every cap, verdict and piece of evidence is produced or enforced by a script and stored in a committed file, because the platform will truncate prompts, isolate subagents from session context, and let an agent argue with anything that is only prose.

What this implies going forward is a change in what to measure. The repos with the most stars (ponytail, mattpocock, Superpowers, taste-skill) earned them with small prompts and published benchmarks, while the only systems that actually ship PRs unattended (marshal, Archon) have 16 and 23,000 stars and run on daemons; popularity is not a guide to factory fitness, and none of the 33 sources publishes success-rate or cost-per-feature data a solo developer could plan against. The v1 above is therefore also an instrument: its `state.json`, `evidence.json` and `log.md` give you tokens per stage, rounds per ticket and escalation reasons from the first run, and the decision to add Linear, Figma, Modal, auto-merge or parallel workers should be made from those numbers rather than from either diagram.
