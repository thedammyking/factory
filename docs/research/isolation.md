# Isolation: Modal sandboxes versus local parallel runs

Ticket [#8](https://github.com/thedammyking/factory/issues/8), researched 2026-11-02 from primary sources only (vendor docs, specs, source code). Background: [design.md, "Every optional integration costs something"](https://github.com/thedammyking/factory/blob/main/docs/design/design.md#every-optional-integration-costs-something-most-belong-in-v2-or-v3). Lines marked *(inference)* are my reading of the cited docs, not a statement in them.

## Answer

- A Modal Sandbox is one disposable gVisor container or VM per task, with tunnels, filesystem snapshots, a beta TLS domain allowlist and per-second billing (about $0.38/hour for 2 cores and 4 GiB). It fans out well, but it is Linux-only and the app under test must run inside it.
- Locally, a git worktree isolates files only. The Claude Code Bash sandbox and `srt` restrict what a process can read, write and reach; both break Chromium on Linux, the Bash sandbox breaks Docker, and Linux `localhost` becomes private to the sandbox. Containers share the host kernel. Docker Sandboxes (microVM) is the only local option with a VM boundary.
- None of them isolate ports, databases or simulators. Each parallel run needs its own allocation: OS-assigned ports, a database copied from a template, a cloned or serialised simulator.
- For the factory: keep v1 single-run; for v2 use a worktree per ticket plus a per-run resource block; prefer `srt` or Docker Sandboxes over Modal for unattended containment; leave Modal at v3 for web-only parallel E2E or untrusted repos.

## What Modal provides

| Capability | What the docs say |
|---|---|
| Isolation | `runtime="gvisor"` (Google's container runtime, "suitable for most workloads") or `runtime="vm"` (own Linux kernel; needed for Docker inside the sandbox, FUSE, nested cgroups). GPUs only with gVisor. Nested virtualisation is Enterprise-only. [Sandbox guide](https://modal.com/docs/guide/sandbox) |
| Isolation guarantee | None promised. Modal describes mechanisms and monitoring, and puts egress limits, resource limits, timeouts and secret hygiene on the customer. [Security](https://modal.com/docs/guide/security) |
| Lifecycle | Created, scheduled, started, ready (optional TCP or exec probe), finished. Default lifetime 5 min, maximum 24 h; `idle_timeout` counts running `exec`, stdin writes and open tunnel connections as activity. Terminate = SIGKILL (exit 137). [Sandbox guide](https://modal.com/docs/guide/sandbox) |
| Resources | Defaults 0.125 core and 128 MiB; sandboxes burst above the request and are billed `max(request, actual)`. VM root disk is a fixed 512 GiB. [Resources](https://modal.com/docs/guide/sandbox-resources), [Sandbox guide](https://modal.com/docs/guide/sandbox) |
| Snapshots | Filesystem snapshot (diff from base image, excludes Volumes, 30-day default TTL, many sandboxes can start from one). Directory snapshot (mountable into a running sandbox). Memory snapshot is alpha: 7-day expiry, taking it terminates the sandbox, no GPUs, TCP connections drop. [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) |
| Tunnels | Declare `encrypted_ports`, `h2_ports` or raw ports at creation; read URLs from `sb.tunnels()`. Connect Tokens are the recommended auth for HTTP and WebSocket; `inbound_cidr_allowlist` is not enforced on unencrypted tunnels. [Networking](https://modal.com/docs/guide/sandbox-networking) |
| Network egress | Default: no inbound, all public outbound allowed. `block_network`, `outbound_cidr_allowlist`, and `outbound_domain_allowlist` (Beta, port 443 only, matched on TLS SNI, domain fronting possible). Policy can be changed on a running sandbox (alpha). [Networking](https://modal.com/docs/guide/sandbox-networking) |
| Docker inside | Requires `runtime="vm"`; run `dockerd` as entrypoint with an exec readiness probe; `/var/lib/docker` is included in filesystem snapshots. [Sandbox guide](https://modal.com/docs/guide/sandbox) |
| Parallelism | The reference docs give no rate or count limit. Plan limits: Starter 100 containers, Team 5,000. Modal's own marketing claims creation above 10,000/s and under-1-second starts; treat as unmeasured. [Product page](https://modal.com/products/sandboxes), [Pricing](https://modal.com/pricing) |
| Claude Code | Official example installs the CLI from `claude.ai/install.sh`, authenticates with `ANTHROPIC_API_KEY` from a Modal Secret, runs one `claude -p` prompt with a PTY, and returns stdout. No ports, volumes, timeouts or parallelism. [Example](https://modal.com/docs/examples/sandbox_agent) |

**Cost** ([Pricing](https://modal.com/pricing)): sandboxes bill at 3x list. $0.00003942 per physical core-second (about $0.1419/h; one physical core is 2 vCPU) and $0.00000667 per GiB-second (about $0.0240/h). My arithmetic: 2 cores + 4 GiB = about $0.38/h. Four of them for 15 minutes = about $0.38. The Starter plan's $30/month credit is about 79 sandbox-hours at that size. Volumes $0.09/GiB-month, egress $0.04/GiB beyond the plan allowance.

**Gaps.** No documented start or snapshot-restore latency (only the marketing claim above). Nothing on running Chromium under gVisor. No iOS Simulator (Linux only, *inference*). Android emulator relies on KVM, HVF or WHPX acceleration; software mode is unsupported and very slow ([Android](https://developer.android.com/studio/run/emulator-commandline)), and Modal offers nested virtualisation only on Enterprise.

**First-party alternative.** Claude Code cloud sessions run in an Anthropic-managed VM behind a default-allowlist proxy, need a Claude subscription, and need a GitHub account unless launched with `claude --cloud` ([sandbox environments](https://code.claude.com/docs/en/sandbox-environments)).

## Local options compared

No primary source publishes start times for worktrees, the Bash sandbox, `srt`, dev containers or plain Docker. The only figures are Docker Sandboxes ("seconds" after the first image pull, [get started](https://docs.docker.com/ai/sandboxes/get-started/)), Modal's marketing claim, and the simulator and emulator snapshot paths below. Anything else must be measured by the v2 setup proof step.

| Option | Isolation strength | Start time | What breaks |
|---|---|---|---|
| **Git worktree** ([git](https://git-scm.com/docs/git-worktree), [Claude Code](https://code.claude.com/docs/en/worktrees)) | Own files, `HEAD`, index. Shares the object store, `refs/` and config. One branch per worktree. Claude Code blocks edits, `cwd` and git redirects that target the main checkout, but not `cp` or shell redirects. No process, network, port or DB isolation ("worktrees isolate file edits"). | Unpublished. Tracked files only; dependency install is extra. A fetch capped at 5 s runs if the repo was not fetched in 24 h. | No dependencies installed. Gitignored `.env` missing unless `.worktreeinclude`. LFS pointer files after `git lfs install --local`. Multiple checkouts with submodules "NOT recommended". Fixed ports and a shared DB collide. |
| **Claude Code Bash sandbox** ([sandboxing](https://code.claude.com/docs/en/sandboxing)) | Seatbelt (macOS) or bubblewrap (Linux, WSL2) on Bash, PowerShell and Monitor commands and their children. File tools, MCP servers and hooks run outside it ([environments](https://code.claude.com/docs/en/sandbox-environments)). Off by default. Network allowlist starts empty; TLS is not inspected, so fronting can bypass it. Subagents inherit it. | Not stated. | `docker` incompatible. Chromium on Linux fails ("No usable sandbox!") unless `allowNestedUserNamespaces`, which disables a boundary. Linux: `localhost` is private to each command and `allowLocalBinding` is ignored. macOS: needs `allowLocalBinding: true`. `jest` needs `--no-watchman`. DB clients and plain `ssh` ignore the proxy. `open` and `osascript` fail on Apple Events, so launching Simulator.app is likely blocked (*inference*; `simctl` is not covered). `excludedCommands` matches the call text only (scripts and `make` targets do not match) and runs with full access. Chromium on macOS is not documented. |
| **`srt`** ([README](https://github.com/anthropics/sandbox-runtime), [environments](https://code.claude.com/docs/en/sandbox-environments)) | Same mechanisms, wrapping the whole Claude process (tools, hooks, MCP). "Beta research preview." Network and writes denied by default; Unix sockets blocked. Linux `enableWeakerNestedSandbox` (for use inside Docker) "considerably weakens" it. Linux deny list is built once at launch. | Not stated. | Linux: Chromium and Electron namespace sandboxes, rootless Podman, nested `bwrap`/`srt`. Docker socket stays blocked unless allowed, and allowing it hands over the host. Tools that ignore `HTTP_PROXY` cannot connect. Linux `localhost` is the sandbox's own loopback, so a dev server and browser inside one `srt` can talk and the host cannot reach them. Windows is alpha. |
| **Dev container** ([Claude Code](https://code.claude.com/docs/en/devcontainer), [spec](https://containers.dev/implementors/json_reference/)) | Container: shared host kernel ([Docker](https://docs.docker.com/ai/sandboxes/security/isolation/)). Reference config adds a default-deny `iptables` firewall (`NET_ADMIN`, `NET_RAW`). Non-root user permits `--dangerously-skip-permissions`. Workspace is bind-mounted writable; a bypassed session can still exfiltrate `~/.claude` credentials. | Not stated (build, then rebuild). | Playwright recommends `--init` and `--ipc=host` for Chromium, and a seccomp profile (or `SYS_ADMIN`) to keep its sandbox ([Playwright](https://playwright.dev/docs/docker)). Host `localhost` unreachable by name (`--add-host=hostmachine:host-gateway`). `forwardPorts` and `appPort` are fixed numbers, so two instances collide. Use `${devcontainerId}` for per-container volumes. A worktree's `.git` file points to the main repo by absolute path by default ([git](https://git-scm.com/docs/git-worktree)), so mounting only the worktree breaks git (*inference*). iOS Simulator cannot run in a Linux container (*inference*). |
| **Plain Docker** ([ports](https://docs.docker.com/engine/network/port-publishing/), [run](https://docs.docker.com/reference/cli/docker/container/run/)) | Shared kernel; you own mounts, seccomp and egress. `-p` binds all host addresses unless you give `127.0.0.1`. `-P` publishes exposed ports on random ephemeral host ports. | Not stated. | Same as dev container. Docker-in-sandbox is blocked by the Bash sandbox. |
| **Docker Sandboxes (`sbx`)** ([architecture](https://docs.docker.com/ai/sandboxes/architecture/), [isolation](https://docs.docker.com/ai/sandboxes/security/isolation/), [git](https://docs.docker.com/ai/sandboxes/workflows/git/)) | microVM per sandbox with its own kernel, its own Docker Engine and image cache, and a host-side proxy for network policy and credential injection. Clone mode gives the agent a private clone (own index, refs, tree). Local use is free. Claude subscription login via `/login` works ([get started](https://docs.docker.com/ai/sandboxes/get-started/)). | First run pulls the image; later runs start "in seconds". | A host worktree gives the agent no git access (the `.git` pointer does not resolve). Clone mode does not separate tasks within one sandbox; use a worktree per task inside it, or separate sandboxes. Read-only mount still exposes `.env`. SSH-agent forwarding is on by default. Hardware and OS requirements not verified (install page not read). Published host ports are ephemeral by default; behaviour when two sandboxes pin the same port is undocumented. |

### Ports, databases, simulators

| Resource | Collision | Per-run mechanism (source) |
|---|---|---|
| Ports | Two runs bind the same dev-server port. Playwright's `webServer` with `reuseExistingServer: true` silently reuses whatever already listens, so run B would test run A's code ([webServer](https://playwright.dev/docs/test-webserver)). | Bind port `0` and read the assigned one ([Node](https://nodejs.org/api/net.html)); Docker `-P` ([run](https://docs.docker.com/reference/cli/docker/container/run/)). Playwright's worker indexes cover per-worker resources but the docs say nothing on ports ([parallel](https://playwright.dev/docs/test-parallel)). On Linux the Bash sandbox and `srt` give each command its own loopback, so fixed ports do not collide there; on macOS they share the host's *(inference from the `allowLocalBinding` text)*. |
| Database | Shared schema and data across runs. | PostgreSQL `CREATE DATABASE ... TEMPLATE` copies a database, but no other session may be connected to the template while it copies ([templates](https://www.postgresql.org/docs/current/manage-ag-templatedbs.html)). Default `WAL_LOG` suits small templates; `FILE_COPY` writes less WAL but forces a checkpoint before and after ([reference](https://www.postgresql.org/docs/current/sql-createdatabase.html)). Playwright's `parallelIndex` can name per-worker resources ([parallel](https://playwright.dev/docs/test-parallel)). |
| iOS Simulator | Shared devices, memory, GPU. | `simctl clone` copies a shut-down simulator using APFS cloning, so clones skip first boot and use little disk. Simulator does not enforce memory or CPU limits, and no maximum count is given ([WWDC19 418](https://developer.apple.com/videos/play/wwdc2019/418/)). |
| Android emulator | Console and `adb` port pairs. | Pairs run 5554 to 5682 (64 devices); the emulator will not start if a port is taken. `-snapshot` resumes a saved state, "usually significantly faster" than a full boot ([emulator CLI](https://developer.android.com/studio/run/emulator-commandline)). |

## Implications for the factory

**Keep**
- **One run at a time in v1, `ACTIVE` lock.** Worktrees isolate files only, so parallelism buys nothing until ports, DB and simulators are solved. The design's note that the lock "becomes per-worktree" stays correct ([design](https://github.com/thedammyking/factory/blob/main/docs/design/design.md)).
- **Bash sandbox with narrow `excludedCommands` for day-to-day work.** Caveat: the stages that matter for E2E (Chromium, dev server on Linux, Docker, Simulator) are exactly the ones that need exclusion, and an excluded command has full access. Exclude the factory's own capture scripts by their literal command text, not whole tools.
- **Modal at v3.** Nothing here makes it cheaper or easier than local options for a single user's laptop.

**Change for v2 (parallel implementers)**
1. **Worktree per ticket**, via `isolation: worktree` or `claude -w`. Setup must install dependencies and copy `.env` through `.worktreeinclude`. Record the base SHA as claude-squad does (`rev-parse HEAD` then `worktree add -b <branch> <path> <sha>`, [worktree_ops.go](https://github.com/smtg-ai/claude-squad/blob/main/session/git/worktree_ops.go)). Let Claude Code prompt before removing a worktree that holds work; claude-squad's `worktree remove -f` plus `branch -D` discards it.
   - *Benefit:* no new infrastructure, and the design's dry run already merged two parallel tickets green.
   - *Trade-off:* a shared object store and refs; one install per worktree (disk, time); implementers that run integration tests still need their own DB.
2. **A per-run resource block** (for example `runs/<id>/env.json`) holding ports, DB name and simulator ID, read by every script. The draft [`run-apps.sh`](../../drafts/scripts/run-apps.sh) has fixed ports (8787, 5173) with `--strictPort`, reads one global `ACTIVE`, and `down` runs `fuser -k` by port, which would kill a sibling run's servers. Allocate ports by binding `0`, kill by recorded PID, and set `reuseExistingServer: false` in generated Playwright config.
   - *Benefit:* parallel E2E on one machine without new tooling.
   - *Trade-off:* every script and the recipe must read the block; URLs are no longer stable across runs, which affects pinned specs and screenshots.
3. **Database per run** via a recipe-declared command. Postgres `TEMPLATE` is the documented route: seed once, copy per run. Create copies one at a time, because the template must have no other connections.
   - *Trade-off:* only helps stacks with a copyable DB; others need their own recipe entry.
4. **Serialise simulators and emulators in v2** with a lock. `simctl clone` and Android snapshots make parallel devices possible but cost RAM and CPU the simulator does not cap, and parallel mobile capture is not needed for correctness.

**Unattended containment (v2 to v3)**
- Prefer `srt` (no Docker, covers hooks and MCP) or Docker Sandboxes (VM boundary, subscription login, clone mode, free) over Modal. Put the dev server and the browser inside the same boundary, since Linux `localhost` is private per sandbox. Use `sbx` clone mode and pull results with `git fetch sandbox-<name>`, not a host worktree.
  - *Trade-offs:* `srt` is a beta research preview and breaks Chromium on Linux; `sbx` hardware support is unverified, and untracked `.factory/runs/` state will not travel into a clone (*inference*). Both need a v2 smoke test before being promised.

**Modal (v3), when it earns its cost**
- Fits: web-only E2E too heavy for the laptop, or third-party repos. Build a named image with dependencies and browsers once, snapshot the filesystem after install, then start N sandboxes from the snapshot; each runs the app and Playwright inside and returns results via `exec` output or a Volume (the example has no file transfer). About $0.38/h per 2-core/4 GiB sandbox.
- Costs: API-key billing instead of the subscription (the only documented path is the example's), no iOS, Android only on Enterprise, Chromium-under-gVisor unproven, domain allowlist is Beta and TLS-only, secrets must be shipped in, and the factory takes a Python or TS SDK dependency.
- **Correction to the design table:** "no published start or snapshot latency" is true of the docs, but Modal's product page does claim under-one-second starts. Keep it labelled as an unmeasured marketing claim.

## Not verified

- Start times for worktree, Bash sandbox, `srt`, dev container and Docker: unpublished; measure.
- Chromium under Seatbelt on macOS, and Chromium under gVisor on Modal: undocumented.
- Docker Sandboxes platform and hardware requirements; same-host-port behaviour across sandboxes.
- Whether Modal sandbox creation has a rate limit below the marketing claim.
